*Step 2 of 4 of the config-profiles migration. **`argus.toml` ceases to exist.**
It is `argus.sandbox.toml`, the profile that selects it lives in a file that is
not in git and not in the image (`/etc/argus/host.env`), and
`scripts/argus-deploy.sh` reads the loaded config's fingerprint back after every
restart. v0.3.17 built a mechanism against files still carrying their old names;
this is the release that actually moves them, and it is the one that turns the
fingerprint from a field on a page into an assertion that can fail a deploy.
**The live cutover is now one line of one file changing on one host** — not a
commit, not a rename, not a copy of `argus.toml` over another `argus.toml`.*

*Named per the Argus's Eyes convention (`docs/releases/README.md`). The pool is
still **Aldebaran** (reserved for the live-min-size flip or a genuinely
uneventful week) and **Rastaban** (reserved for dual-watchdog / consensus
verification) — neither fits, so the name comes from outside the table again,
the pattern since v0.3.6. **Alhena** — γ Geminorum, Arabic *al-han'ah*, the
**brand mark** burned into a camel's neck to say whose it is — is the release in
one word. Every part of this is a thing that now carries its own identifying
mark and a reader that checks it: the config file is named by its profile, the
host declares which profile is its own, the mount keeps the profile in the
filename inside the container, and the deploy reads the mark back off the
startup line before it calls the deploy done. It qualifies by **tradition, not
by "eye" etymology** — it sits in the same Arabic asterism grouping as **Tejat**
(μ Gem, "the Eye"), spent on v0.3.13 — the same standing already granted to
Alcor, Alterf, Grumium and Alsciaukat. **Aldebaran and Rastaban stay reserved**:
this adds no second verification loop and it is not a clean re-watch.*

**Code + config + HOST release, and the host half must be done FIRST.**
`/etc/argus/host.env` has to exist on the droplet **before** this deploy, or
`argus.service` will not start — deliberately (see Deploy, below). `src/` changes
are small (one loader refusal); the substance is `argus.service`,
`docker-compose.yml`, `Dockerfile`, `scripts/argus-deploy.sh`, the file rename,
and the docs. **`Dockerfile` moved, so this is a BUILD release** — `build: YES`
in the plan, not config-only.
**No config KEY changed shape**, so an old image reads the renamed file
unchanged.

## Changed

**`argus.toml` → `argus.sandbox.toml`, and the old name is `.gitignore`d.** All
three configs are now named by profile (`argus.dev.toml`, `argus.sandbox.toml`,
`argus.live.toml`). The old name is ignored rather than merely deleted because a
stray copy — a hand-made backup, a half-finished cutover, muscle memory — must
not be committable: it carries no profile, so `_check_profile` would not be
armed on it, and `/status` would render it amber saying exactly that.
`tests/test_config_profiles.py` moved with the rename and gained two assertions:
that the old name is gone and ignored, and that **no fourth
`argus.<profile>.toml` can appear without being listed** in `PROFILE_FILES` — an
unlisted profile file would sit outside every assertion in that module, which is
the state the module exists to prevent, one file over.

**The profile reaches the container from a file that is not in git.**
`argus.service` gains:

```
EnvironmentFile=/etc/argus/host.env
```

Root-owned, mode 600, per host, one line (`ARGUS_ENV=sandbox`). **No `-`
prefix**, deliberately: a missing file must fail the *unit* loudly rather than
start it with the variable unset and let compose refuse one layer further from
the cause. It is deliberately **not** `./.env`, which is hand-edited, never
touched by the deploy, and already the documented trap for `ARGUS_IMAGE_TAG`.

`docker-compose.yml` interpolates it:

```yaml
ARGUS_ENV: ${ARGUS_ENV:?ARGUS_ENV must be set — see /etc/argus/host.env}
ARGUS_CONFIG_DIR: /etc/argus
volumes:
  - ./argus.${ARGUS_ENV}.toml:/etc/argus/argus.${ARGUS_ENV}.toml:ro
```

Three things in that block are load-bearing. **`${VAR:?}` and never
`${ARGUS_ENV:-sandbox}`** — a default is precisely how the wrong config gets
deployed quietly, which is the failure class the whole profile model exists to
close, and it would be silently wrong on the one host where it matters, since
the cutover *is* that variable changing. **`ARGUS_CONFIG` is now UNSET** — an
explicit path WINS over the profile (`config.resolve_config_path`), so leaving it
set would reduce `ARGUS_ENV` to decorating a filename it no longer selects, and
`/status` could no longer report which profile was armed. And **the mount keeps
the profile in the filename inside the container**: mounting to a fixed
`/etc/argus/argus.toml` would work, would be one fewer moving part, and would
disarm the filename↔environment assertion entirely.

**The image no longer carries an answer to "which config?" — found while wiring
this up, and it would have defeated the whole mechanism.** The `Dockerfile`
shipped two image-level defaults that nothing in v0.3.17 touched:
`ENV ARGUS_CONFIG=/etc/argus/argus.toml`, and
`COPY argus.toml /etc/argus/argus.toml` ("a baked default config so the image runs
standalone"). Both are gone.

- **The ENV wins over the profile.** `config.resolve_config_path` gives an
  explicit path precedence over `ARGUS_ENV` — correctly — so with compose's
  `ARGUS_CONFIG` removed the image's own would have taken over silently: the
  profile naming a file nothing loads, and `/status` reporting a profile the
  loader ignored. An image-level default config path is exactly the shape v0.3.17
  deleted from the code, one layer down.
- **The baked COPY is the sharper one: it is the single failure the fingerprint
  cannot see.** It sat at the same path the bind mount targets, so a drifted or
  missing mount fell back to it — and because both copies come from the same git
  checkout, **the sha would have MATCHED** and the new read-back would have passed
  a config that was never mounted. With nothing baked, a drifted mount is a hard
  `ConfigError` on every profile.

The rename would have failed the build loudly (`COPY argus.toml` of a file that no
longer exists), so this was going to surface — but as a build error at deploy time,
not as the reasoning above. `tests/test_deploy_wiring.py` now asserts the image
declares no `ARGUS_CONFIG` and bakes no `argus.*.toml`.

**A profile with no file is a `ConfigError`, not a traceback.** Docker creates a
bind-mount source that does not exist on the host as a **directory**, so
`ARGUS_ENV` naming a profile with no `argus.<profile>.toml` beside the compose
file reached `Config.load`'s `read_bytes` as `IsADirectoryError` and read as a
crash. `load` now answers `OSError` with its own fail-closed sentence
(`config file is not readable: …`), because the loader's refusals are the
process's. This is the one `src/` behaviour change in the release, and it exists
because step 2 made that shape reachable through the deploy.

**Every `docker compose` command on the droplet now needs `ARGUS_ENV`** — not
just `up`, but `build`, `run`, `ps` and `down`, because compose interpolates the
file before doing anything. **`sudo` scrubs the environment**, so it goes on
sudo's own command line:

```bash
sudo ARGUS_ENV=sandbox docker compose -f /opt/argus/docker-compose.yml ps
```

Under the service it arrives from `EnvironmentFile` and nothing has to be typed.
README §4 and runbook §17 are updated throughout for this, along with every
`--config /etc/argus/argus.toml` example.

## Added

**`scripts/argus-deploy.sh` verifies the config, on every release class.** Five
changes, and the last is the one the whole design was for:

1. **It resolves the profile from `/etc/argus/host.env`** — the same file systemd
   reads, never a default, never inferred from the branch — and prints it in the
   plan. It refuses if that file is unreadable or carries no usable `ARGUS_ENV`,
   with the provisioning commands in the error.
2. **It refuses a tag that does not contain `argus.<profile>.toml`**, checked
   against the tag rather than the working tree so `--dry-run` answers it too.
   That failure otherwise presents as a crash loop at restart, via the
   missing-mount-becomes-a-directory shape above.
3. **A named `CONFIG_INPUTS` class**, so the plan *states* `config: YES` with the
   files that moved, instead of leaving the operator to deduce "config-only" from
   the absence of a build. `docker-compose.yml`, `fomc_dates.txt` and
   `discretionary_blackout_dates.txt` count alongside the three configs and
   `blackout_dates.txt`.
4. **`--dry-run` diffs this host's config** between the deployed tag and the
   target. **On a config-only release that diff IS the release** — there is no
   source change to read instead — and it is the last moment before risk rails,
   staleness bounds and COA timing change under a restart. Only this host's
   profile is diffed; the other files are not mounted here and would bury the
   one that is.
5. **It reads the fingerprint back after the restart, on EVERY class.** The
   expected sha is computed from the tag *and* re-checked against the working
   tree after checkout (the mount reads the tree, not the git object). Afterwards
   it parses the same `argus build` line the version read-back already anchors
   on:

   ```
   argus build v0.3.18 config sandbox/argus.sandbox.toml @be5c42777173
   ```

   The **profile/filename** half is compared too, not just the sha: a mismatch
   there is a drifted mount or a stale `ARGUS_CONFIG` in `./.env` winning over
   the profile, which a hash comparison alone would report as an unexplained
   number. A missing fingerprint is a WARNING, not a failure — that is what a
   rollback to a pre-v0.3.17 image legitimately looks like.

   **Unlike the version read-back, this is not gated on having built.** The
   version check is correctly skipped on a config-only release, because the image
   is deliberately untouched there and the running version legitimately still
   names the previous tag. That is exactly why the config half must run: before
   this, a config-only release verified **nothing**, and "the new config loaded",
   "the restart beat the checkout", "the mount drifted" and "somebody hand-edited
   the droplet and it has not restarted since" were indistinguishable.

**`tests/test_deploy_wiring.py` — nine assertions over three non-Python files.**
`argus.service`, `docker-compose.yml` and `argus-deploy.sh` decide which config
the droplet loads, and a unit test of `resolve_config_path` proves the loader is
right while saying nothing about whether the profile ever reaches it. So: compose
refuses rather than defaults and sets no `ARGUS_CONFIG`; the mount keeps the
profile in the filename; the unit's `EnvironmentFile` has no `-`; the deploy
never guesses the profile, *compares* rather than merely prints, cuts exactly
`CONFIG_SHA_LEN` hex (two implementations of one number, invisible from either
side), names the release class, and **keeps the config read-back outside the
`NEED_BUILD` guard**. Comments are stripped before every assertion — compose
writes `${ARGUS_ENV:-sandbox}` out in prose precisely to say never to write it.
Same reasoning as `tests/test_build_version.py`: prose and script are two
implementations of one procedure, and only one of them gets read by a human who
can notice.

## Deploy

**Provision the profile FIRST. The service will not start without it.**

```bash
# ON THE DROPLET, BEFORE ANYTHING ELSE
sudo install -d -m 700 /etc/argus
printf 'ARGUS_ENV=sandbox\n' | sudo tee /etc/argus/host.env >/dev/null
sudo chmod 600 /etc/argus/host.env
sudo cat /etc/argus/host.env          # exactly one line: ARGUS_ENV=sandbox

# And make sure ./.env carries no leftover ARGUS_CONFIG — an explicit path WINS
# over the profile, and env_file entries reach the container.
grep -n ARGUS_CONFIG /opt/argus/.env  # must print nothing
```

Then the ordinary sequence. **`argus.service` changed, so the unit must be
re-copied and `daemon-reload`ed** — `scripts/argus-deploy.sh` does that itself
when it sees the unit move, which it will on this release:

```bash
cd /opt/argus
scripts/argus-deploy.sh --dry-run v0.3.18   # read the plan AND the config diff
scripts/argus-deploy.sh v0.3.18
```

By hand, if you would rather:

```bash
cd /opt/argus
git checkout v0.3.18
git describe --tags && git status --short   # must be the tag, must be clean

PROFILE="$(sudo sed -n 's/^ARGUS_ENV=//p' /etc/argus/host.env)"
sha256sum "argus.${PROFILE}.toml" | cut -c1-12    # the sha you expect below

sudo ARGUS_ENV="$PROFILE" docker compose build \
     --build-arg ARGUS_VERSION=$(git describe --tags --always --dirty)
sudo docker tag argus:local argus:v0.3.18

sudo cp argus.service /etc/systemd/system/argus.service   # THE UNIT MOVED
sudo systemctl daemon-reload
sudo systemctl restart argus.service

sudo journalctl -u argus.service -n 50 | grep 'argus build'
curl -fsS -H "Authorization: Bearer $ARGUS_KILL_TOKEN" \
     http://<tailscale-ip>:8443/status | jq '{version, config}'
```

**After deploy, what to look for.** `/status`'s `config` object should now read
`{"profile": "sandbox", "file": "argus.sandbox.toml", "sha": "be5c42777173"}` —
and the **`profile` is no longer `null`**. On v0.3.17 it legitimately read `null`
and the row rendered amber, because compose still mounted the profile-less
`argus.toml`; that was correct then and is a fault now.

**The sha does not change across this deploy, and that is the useful part.** The
rename moved no bytes, so cert's config still hashes `be5c42777173` — the value
`/status` has been reporting since v0.3.17 went out. Only `profile` and `file`
move. If the sha *does* change, something edited the file, and this is the first
release where that question has an answer. Nothing about trading behaviour changes: the
`environment` key still decides everything it always did, and no REQUIRED config
key changed value or shape.

**Rollback has a new first step.** `git checkout v0.3.17` restores the old
filenames *in the tree*, but the deployed `argus.service` on the droplet would
still carry `EnvironmentFile=` and compose would still be the old one — so roll
back the unit too:

```bash
scripts/argus-deploy.sh v0.3.17     # restores argus.toml, compose, and the unit
```

`/etc/argus/host.env` can simply be left in place; nothing on v0.3.17 reads it,
and leaving it means a re-deploy forward needs no re-provisioning. Because no
config key changed shape, a v0.3.17 image against a v0.3.18 tree (or the reverse)
loads fine — what breaks a half-rollback is the *mount path*, which is why both
halves must move.

**Deliberately NOT in this release, staged as steps 3–4:**

- **The cert promotion of `unmanaged_order_cancel`** (F2) — the first intended
  exercise of the config-only release path, now that the path finally asserts
  something. A test asserts `false` in all three profile files, so the flip costs
  an explicit, reviewed edit rather than a silent one.
- **The live cutover.** After step 3 it is: change one line of
  `/etc/argus/host.env`, restart, and read the fingerprint back. The live config
  has been loaded by a test since v0.3.17 and its key set pinned since then.
- **Cert risk sizing in `argus.live.toml`** (F3) — still cert's numbers, decided
  at the live-min-size gate, not here.
- `argus.dev.toml`'s `signal.max_width` (F5) — still allowlisted with its
  reasoning rather than fixed.
- **No config hot-reload, and none is planned.** A config release is still a
  restart: config is read once at startup, half of it into frozen objects at
  session build, and risk rails changing under a live position is strictly worse
  than a scheduled restart.

**A deliberate non-sweep, stated so the next reader does not mistake it for an
oversight:** generic prose in `src/` docstrings that says "in argus.toml" meaning
"in the config" was left alone. What was changed is everything **executable or
copy-pasteable** — usage examples, argparse help, printed operator messages, and
every command in `README.md` and the runbook — plus the comments that described a
state this release ended. A comment that reads as shorthand for "the config file"
is not a landmine; a command that names a file which no longer exists is.

**Verified against the real image before shipping**, since three of the failure
modes above only exist inside a container: a build with the new `Dockerfile`
stamps cleanly; `ARGUS_ENV=sandbox` + `ARGUS_CONFIG_DIR=/etc/argus` resolves to
`ConfigSource(profile='sandbox', file='argus.sandbox.toml', sha='be5c42777173')`
— the same sha the droplet reports today; a bare `Config.load()` in the image
refuses with `no config selected` and `/etc/argus/argus.toml` does not exist; and
a profile with no matching file arrives as
`config file is not readable: … [Errno 21] Is a directory`, confirming both the
Docker behaviour and the new refusal. `docker compose config` also refuses with
`required variable ARGUS_ENV is missing a value` when the profile is unset.

**The daily max-loss circuit breaker remains structurally inert in sandbox**,
unchanged by this release. Proving that rail out is still a live-flip gate.

**Test suite: 1997 passing, up from 1984 at v0.3.17** — 13 new: 10 in the new
`tests/test_deploy_wiring.py`, 2 in `tests/test_config_profiles.py` (the old name
is gone and ignored; no profile file may go unlisted), and 1 in
`tests/test_config.py` for the directory-shaped config refusal. Four existing
tests moved to the new filename, and two were widened to cover `argus.live.toml`
alongside the others — the blackout being enabled, and `unmanaged_order_cancel`
being `false` — because live is the profile no session has ever started.
