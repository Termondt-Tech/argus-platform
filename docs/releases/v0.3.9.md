# v0.3.9 — Oculus

*π Capricorni, "Oculus" — Latin for Eye, marking the right eye of the Sea Goat
in classical fixed-star astrology. Two gaps found by living through the exact
sequence that exposes them: an evening restart after a day that held 0DTE
positions to expiry, followed by a morning session with no ledger reset in
between. One made the halt too conservative past the point it could still be
right; the other left the watchdog reporting a position that had already,
correctly, stopped existing.*

> Found outside the pool, same as Alterf and Polaris — neither reserved
> candidate fit this release's shape. Proposed by Richard, verified against
> two independent fixed-star sources before being spent here (astrologyking.com,
> geocult.org — both confirm "Oculus" as π Capricorni's traditional name,
> positioned on the Sea Goat's eye in the constellation figure). See
> [releases/README.md](README.md#release-names--arguss-eyes).

Requires an image rebuild — `reconcile.py`, `execution/store.py`,
`execution/watchdog.py`, `session.py`, `app.py`, and `marketcalendar.py` all
change. **No config schema change**: both fixes derive their new input from
existing config (`[market] half_days` / `half_day_close`, already populated
through 2027) rather than adding a key. An old config runs the new image and
vice versa.

## Fixed

**A same-day evening restart, after a day that held 0DTE positions to expiry,
hard-halted until the ET date rolled over — even after settlement, when the
position it was protecting against could not exist.** The 2026-08-12 expiry
carve-out resolves a `missing_at_broker` row only when its own OCC expiry is
strictly before today, reasoned for the intraday case: *"within its own
trading day the position can genuinely still be held."* That reasoning holds
intraday and stops holding once the session settles — SPXW is cash-settled,
European, PM-settled, so a definitively-closed session means the row cannot
describe a live position, whatever the calendar date still says. Hit live:
the `v0.3.8` evening deploy (2026-08-24, 21:02 ET) halted on 4
`missing_at_broker` discrepancies — both of that day's held-to-expiry spreads
— and stayed parked until a manual restart the next morning, past 00:00 ET,
resolved it with no further action.

**Fixed by extending eligibility, not by loosening the floor.** A row now also
resolves when its expiry is today AND today's session has settled — reusing
`tools/mark.py`'s existing `16:15 ET` boundary (*"a quote before this is not
a settlement price"*) rather than inventing a new one, and reading it off
`MarketCalendar` per-day (13:15 on a half-day) rather than a literal 16:00.
`expiry_verdicts` and `reconcile_and_record` both gained a **required
keyword-only `session_settled: bool`** — no default in either direction,
because a default here is a way to get it wrong without knowing the argument
exists: `True` would resolve a still-open 0DTE row at 11:00, `False` would
silently restore the halt this closes. All three call sites build it through
one new function, `session.session_settled`, off the caller's own injectable
clock — never host-local time, never two readings that could straddle
midnight and judge one day's expiry against another day's close. A future
expiry is unaffected either way; only the same-day case gained a second path
to resolution.
→ [expired positions, 2026-08-25 addendum](../decisions/2026-08-12-expired-position-resolution.md#addendum-2026-08-25-the-evening-restart-and-the-legs-left-behind)

**The same rule that resolves an expired `positions` row leaves `order_legs`
behind, and the watchdog's own spread reconstruction had no idea those legs
had expired — producing a permanent false `watchdog.unwatchable` page for a
position that no longer exists.** `execution/store.py`'s `_open_spreads`
rebuilds "what's open" purely from `orders`/`order_legs` attribution, with no
notion of expiry; 0DTE expiry produces no closing order, so a spread held to
expiry stayed "outstanding" by that arithmetic forever. Once `positions` was
cleared (by the fix above, or by any prior reconcile), the two tables
permanently disagreed — the exact divergence check built to catch a real
ledger/broker mismatch, firing on the one cause that isn't one. Confirmed live
the next morning: one Tier 1 `watchdog.unwatchable` page and Tier 2
`watchdog.unwatchable_still` every ~15s, indefinitely, for two positions that
had settled full-credit and no longer existed anywhere. **Confirmed harmless
to trading** — `open_spread_count` only counts the scan's `spreads` list,
never `malformed`, so nothing was ever blocked or miscounted — but a real,
standing false alarm, and the exact `/status`-invisible shape A2b already
named and left unbuilt.

**Fixed by making the scan expiry-aware; `order_legs` itself is untouched.**
A leg whose own OCC expiry is strictly before today is no longer counted as
outstanding, so a fully-expired spread takes the same path a cleanly-closed
one already does — absent from the scan, not `malformed`, not
`unattributed`. `OpenSpreadSource.open_spreads()` gained a **required
keyword-only `today: date`**, same reasoning as above: the dangerous
direction is silent, and a date from the wrong clock drops a LIVE spread off
the watch list. The divergence check itself is unweakened — a leg missing
from `positions` for any reason OTHER than its own expiry still diverges,
still pages, exactly as before; a dedicated test proves it on the identical
ledger shape, differing only in the date it's read as of. Root-caused to
2026-08-17: the overlapping-verticals fix moved holdings to per-idea
`applied_quantity` and stopped reading `positions` for the scan at all, which
quietly falsified this document's own claim that expired legs were "already
skipped" — the comment was true when written and went stale the moment its
collaborator changed, the same shape C2 already found once.
→ [same addendum](../decisions/2026-08-12-expired-position-resolution.md#task-2--expiry-resolved-positions-left-order_legs-behind)

## Deploy

Rebuild only — no config to move with it.

```bash
cd /opt/argus
scripts/argus-deploy.sh --dry-run v0.3.9   # show the plan, touch nothing
scripts/argus-deploy.sh v0.3.9             # deploy it
```

Equivalent manually, per the runbook (§17): `git fetch --tags && git checkout
v0.3.9` (NO sudo on either), verify with `git describe --tags` and
`git status --short`, then `sudo docker compose build && sudo docker tag
argus:local argus:v0.3.9 && sudo systemctl restart argus.service`.

**Rollback needs only one half.** `argus.toml` is unchanged, so either
`git checkout v0.3.8` alone or `ARGUS_IMAGE_TAG=<v0.3.8 image>` alone is a
complete rollback. No dependency change; `requirements.txt` is untouched.

**This release touches the reconciliation halt and the watchdog's watch
list directly** — both are on the path that decides whether trading resumes
after a restart and what the watchdog evaluates stops against. Confirm the
deployed config still matches before restarting, same as every release
before it. Both fixes were exercised live end-to-end (the actual 2026-08-24
evening halt, the actual 2026-08-25 morning false page) before being fixed,
so this is not a theoretical change — it closes exactly the sequence that
already happened.

## Scope

**Closes two gaps in the 2026-08-12 expired-position design, both found by
living through the sequence that exposes them** — an evening restart after a
day held to expiry, with no clean reconcile marker standing to trigger the
broader sandbox reset in between. Neither is a `v0.3.8` regression: the
reconciliation and watchdog code these fixes touch is untouched by `v0.3.8`'s
diff, and both gaps existed in the design since 2026-08-12 / 2026-08-17
respectively. They simply hadn't been exercised — every prior restart either
had a clean reconcile marker standing (letting the broader sandbox reset
clear `order_legs` too, masking Task 2 completely) or landed the next
calendar day already, before Task 1's boundary could bite.

**Recurs on most evening deploys, not a corner case.** Three of the five most
recent trading days (2026-08-24, 08-21, 08-20) held at least one position to
expiry. Any evening release on those days would have hit Task 1, and — absent
this fix — Task 2 the following morning.

**One follow-on finding filed, not fixed here:** `_open_spreads`' ledger read
carries no bound on trading date at all — it scans every `order_legs` row
ever written, forever, on every 15s watchdog refresh. Not urgent (no measured
latency problem yet), but flagged while touching this code as cheaper to fix
now than after the table has run unbounded for months. Tracked in
`docs/tasks/argus_open_spreads_unbounded_ledger_read_prompt.md`, unscheduled.

**The daily max-loss breaker remains structurally inert in sandbox**,
unchanged by this release — day P&L is derived from NLV and cert never marks
NLV. Proving that rail out is still a live-flip gate this release does not
close.

**Unrelated to this release, tracked separately:** the same evening's
investigation also traced a real event-loop-lag mechanism (a failed account
refresh destroying its pooled connection, forcing an unpooled TLS handshake
onto the loop) correlating with production breaches at r=0.695. That fix is
a design task
(`docs/tasks/argus_account_refresh_off_event_loop_prompt.md`), gated on
Richard's sign-off before implementation, targeted at `v0.3.10` or later —
explicitly not bundled into this release.
