## Name

**Rastaban** — β Draconis, Arabic *Rās al-Tinnīn*, "Head of the Serpent/Dragon" — Draco's brighter eye. Its traditional pair, **Eltanin**, was spent on v0.3.12; Rastaban itself is still waiting.

The pool reserved Rastaban for "dual-watchdog / consensus verification. A release that adds a second, independent validation loop or cross-checks one rail's verdict against another before a high-risk action fires."

It fits the release exactly: the stub close fix has two halves that share one invariant but do not trust each other. The watchdog half detects the stub from scan-side evidence (the booking) and arms the send, while the guard half independently cross-checks the quantities against the broker's own order ledger on every ask. The high-risk action (sending the automated close) fires only when both rails agree.

## What changed

### 1. A quantity-aware guard for CLOSE identifiers

The existing `DuplicateOrderGuard` blocked any further close if it saw a `FILLED` disposition under the identifier (which a partial fill gives). It now implements a quantity rule for CLOSE identifiers:

- A close of `q` contracts is permitted iff nothing is WORKING under the identifier, every order under both the close and the sibling OPEN identifier is readable, and for every leg symbol `closed_filled + q ≤ opened_filled`.
- Both sums are taken from the broker's own per-leg fill quantities off the one `get_live_orders()` fetch the guard already makes.
- Fails closed on any unreadable input (`close_quantity_unreadable`, `opened_quantity_unreadable`) or if the inequality fails (`close_quantity_exceeded`).
- Leaves today's binary rule untouched for everything else.

### 2. The stub close continuation

A closing order that fills partially leaves a "stub" (fewer contracts of the same vertical, still held). Previously this was watched and paged but never re-attempted.

- **Detection**: The watchdog detects the stub scan-side (a spent FILLED position the ledger still holds).
- **One allowance**: The stub gets exactly one further close, per candidate, per process lifetime AND across restarts.
- **Durable spend**: The allowance is spent at the handoff and recorded as a Tier 1 `watchdog.stub_close` before the first send. A crash before the send loses the allowance (fail-closed).
- **Paced restores**: Restored in-memory only on proven-no-send values (`NOT_ATTEMPTED` and `BLOCKED`). Every restore is paced one refresh interval, and `BLOCKED` restores are bounded at 3 before staying spent.
- **The switch**: `watchdog.stub_close_enabled` is a REQUIRED strict bool. It ships as `true` in all three profiles because the emergency-stub exposure already exists with the profit target off. It arms both the watchdog half and the guard half.

## Why it's safe

- **Never over-closes**: The inequality `q ≤ opened_filled − closed_filled` ensures the order never exceeds what the broker's order ledger says is open.
- **Never double-closes**: A working order under the identifier still blocks with existing precedence.
- **Fails closed**: Any unreadable order or field results in a refusal, returning to the default state (paged, unsent).
- **Bounded**: The stub continuation gets exactly one allowance per candidate per day.
- **No budget impact**: The stub path never writes `_attempted`, `_sends`, `_flatten_attempted`, or `_profit_spent`.
