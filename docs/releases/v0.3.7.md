# v0.3.7 — Polaris

*α Ursae Minoris — the Pole Star, "the Unmoving Eye": every other star wheels
around it over the course of the night, and it is the one point that holds
still. Every fix in this release is that same shape — state that has to read
the same regardless of what churns around it. A same-day restart no longer
re-arms the daily max-loss breaker or forgets a spent exit attempt on
`/status`; a broker order Argus cannot map no longer disappears from
reconciliation instead of halting it; a book-confirm cache no longer forgets
what it already confirmed the moment the account snapshot changes shape.
Eleven fixes, pointed the same direction: whatever else is moving, the watch
itself does not lose its place.*

> New to the pool this release — qualifies by tradition (the "unmoving eye,"
> not a literal one) rather than etymology, the same standing as Alterf's and
> Alcor's. Neither pool candidate (Aldebaran, reserved for a clean steady
> re-watch or the live-min-size flip; Ain al-Rami, waiting for an aim/targeting
> fit) matched this release's shape, so this name was found rather than picked
> from the table, same as Alterf was. See
> [releases/README.md](README.md#release-names--arguss-eyes).

**Requires an image rebuild AND a config change, and they must deploy together.**
This is a `src/`-heavy release across eleven fixes, and one of them —
[the book-confirm cache](../decisions/2026-08-21-book-confirm-cache-is-per-shape-and-expires.md)
— adds a REQUIRED key, `[watchdog] book_confirm_ttl_s`. A v0.3.7 image against a
pre-v0.3.7 `argus.toml` refuses to start:

```
missing required config key: watchdog.book_confirm_ttl_s
```

See **Deploy** below for the two-halves-not-independently-safe warning this
implies — same shape as v0.3.6's.

Ten of the eleven fixes here need no config change at all; the eleventh needs
exactly one key. **This is one release, not several** — every commit in it sits on
`main` between the `v0.3.6` tag and this one with no intervening tag, spans one
continuous proactive-review pass (2026-08-20 20:13 through 2026-08-21 13:46), and
only the single key above is new. Splitting it would not change what has to deploy
together.

**Found by two different routes, both read rather than incident.** Six were found
by a static proactive-review pass looking for five specific recurring defect
shapes (an invariant reused across a call-path boundary it wasn't built for; a
threshold calibrated on one condition applied to both; a comment describing a
reasoned bound the measured value outran; status derived from a structure the
live state has left; an early return dropping state a caller still assumes). Three
more — A3b, A4b, A2b — were **not predicted by that review**: each surfaced only
once a sibling fix's own test was being written, going one layer deeper than a
static read reaches. See **Methodology**, below the fold.

## Fixed

**The daily max-loss breaker re-armed on every same-day restart, and `/status` had
the same defect one field over.** `DailyLossBreaker`/`DailyPnl` were built bare on
every `_run_session_day`, so a restart at 11:40 came back untripped from an 11:20
trip AND re-anchored day P&L to the post-loss NLV — the loss already taken read as
~0, and the rail needed a *second* full drawdown to re-trip. Cert cannot exercise
this at all (day P&L is structurally 0.0 there), so the mutation-tested restart
simulation is the rail's only coverage. `/status`'s `breaker_tripped` was reading
the audit log's `daily_loss.breach` row, which outlives the process that wrote it,
so the same restart rendered TRIPPED in red while the gate was allowing entries —
the reassuring reading at the one moment it was wrong. Both now read the live
`DailyLossBreaker`/rehydrated state, trading-date-scoped, via a new
`risk/rehydrate.py`. No config key; `src/` only.
→ [restart rehydration](../decisions/2026-08-20-daily-loss-breaker-restart-rehydration.md)

**Unmappable broker orders were silently dropped from `get_live_orders()`, which
also silently dropped them from reconciliation, the duplicate guard, and the exit
path's broker reads.** The adapter's own comment justified the drop by naming the
callers it was safe for — accurate when chunk 1 shipped, false the moment chunk
2's `Reconciler` started calling the same method. One unrecognized status string
was enough to hide an unknown WORKING or FILLED order from the rail whose entire
premise is "halt on anything unexplained," and to make it read as no order at all
to `DuplicateOrderGuard`, the only duplicate-submission protection in the system.
`get_live_orders()` now returns `LiveOrders` — mappable orders plus the unreadable
ones, explicitly, with no `__iter__` to filter them out by accident.
`reconcile_orders` takes the unreadable set as a required keyword argument with no
default. Sandbox/live hard-halt on one at restart; mid-session it announces
(Tier 1 + alert) without taking the watchdog down with it. No config key;
`src/` only.
→ [unmappable orders](../decisions/2026-08-20-unmappable-orders-reach-reconciliation.md)

**The market-crossing exit escalation could double-close a spread on an empty or
partial broker answer.** `_await_settled` read "the broker never mentioned this
order" and "the broker mentioned only its already-abandoned rungs" both as
"nothing is working, safe to send a second closing order" — `any()` over an empty
list is `False`, and every visible row in a partial answer being terminal passed
the same test. Either way the second order went out on top of one still at
`Cancel Requested`, which does not flatten the position, it re-opens it inverted
and unmanaged on expiry day. Two frames away, `PriceWalkingLoop` already treats
the identical signal as a read gap rather than a verdict; the stricter call site
had the weaker rule. Fixed in two passes, same session: only a POSITIVE
confirmation confirms now, scoped to `walk.broker_order_id` specifically — not the
whole `external_identifier`, which several abandoned rungs of one exit legitimately
share. Absent, partial, still-working, and unreadable all retry inside
`exit_cancel_settle_s` and refuse at the deadline with `CROSS_REFUSED`. The FILLED
check stays identifier-wide, deliberately — a fill on any rung means the spread is
flat, and narrowing it would let an earlier rung's fill sit ignored in the same
answer. No config key; `src/` only.
→ [empty answer](../decisions/2026-08-21-empty-broker-answer-is-not-a-verdict.md),
[partial answer](../decisions/2026-08-21-partial-broker-answer-is-not-a-verdict.md)

**The entry path admitted an option leg on presence alone, at any age.**
`DXLinkChainSource.snapshot()`'s only test was `is None` — a wing that quoted once
at 09:31 and never again was joined into every snapshot for the rest of the day.
Nothing downstream caught it: the pre-trade gate's staleness check covers the
underlying only, `execution.signal_max_age_s` measures pipeline latency (~0 by
construction) rather than quote age, and `_assert_credit_matches_legs` recomputes
the credit from the same stale legs — self-consistent, not correct. The exit path
has enforced a per-leg bound since chunk 4; this closes the same gap on entry, one
module short of where it had stopped. Legs now need a quote AND greeks within
`staleness.market_data_max_age_s` — resolved from that key's own definition
("DXLink quote age past which entries are blocked"), so **no new config key**.
Rejection costs a leg its strike, not the tick — the strategy routes to the
next-nearest delta among what's still admitted. **The admission rate this gate
produces is instrumented but not yet measured** — `ChainCoverage.admissible` /
`stale_quote` / `stale_greeks` now print every 15s; measure over a full RTH
session, against `[marketdata] source = "live"` only, before entry size is scaled.
→ [entry leg freshness](../decisions/2026-08-21-entry-leg-quote-freshness-gate.md)

**The watchdog's REST book-confirm was bounded by a rebuild cadence, and the fix
for that exposed how many times the mistake could repeat.** `_cache_is_over_reporting`
wrapped its `fetch_positions()` round trip in `asyncio.timeout(watchdog.refresh_interval_s)`
— 15.0s, a watch-list rebuild cadence with no connection to how long an HTTP call
should be allowed to take. That await sits inside one `check_once` pass, so it was
a **blind window**: up to 15s (15× `cadence_s`, 3× the `sustained_s` debounce) with
no open position evaluated against its triggers, landing on the paging edge of a
book disagreement — the moment the book is least understood. Fixed by using
`staleness.account_refresh_timeout_s` (5.0), the already-tuned per-attempt bound
for this exact call against this broker. Blame confirmed 15s was never a deliberate
choice. Tracing the residual found the cache itself was a single SLOT, collapsing
only *consecutive* repeats of one shape — a book alternating between two shapes
re-confirmed on every alternation, unboundedly, and a persistent account-cache
ghost is exactly that alternation. It is now a shape-keyed dict with an explicit
three-part staleness policy — the episode (cleared outright on agreement), the
shape, and a hard ceiling, `watchdog.book_confirm_ttl_s` — because a cached `True`
suppresses `held_but_unbooked`, the one condition deliberately built with no timer
allowance. All three fail toward asking REST again; nothing in the policy can
produce a suppression a fresh confirm would not have. **New required key**:
`watchdog.book_confirm_ttl_s = 90.0`, floored above `refresh_interval_s` by the
loader. Rides the coupled deploy this release already needs.
→ [book-confirm timeout](../decisions/2026-08-21-book-confirm-timeout-bound.md),
[per-shape confirm cache](../decisions/2026-08-21-book-confirm-cache-is-per-shape-and-expires.md)

**A triggered position whose exit attempt failed to resolve had no automated path
to close and nowhere to be seen.** `WalkPolicy.for_exit` shares `working_timeout_s`
and `max_recovery_attempts` with the entry policy on the reasoning that both "touch
no price" — re-derived against the exit's actual risk profile, that reasoning
holds and shortening either value would have made things worse (`NEVER_WORKED` /
`UNRESOLVED` spend the position's one exit attempt; reaching them sooner is not an
improvement). The defect was the STATE those outcomes land in, not the seconds:
`_attempted` made `check_once` skip the position for the rest of the process — no
trigger evaluated, gone from `/status`'s impaired cell, and no automated path to
close at all (there is no EOD flatten anywhere in `src/`) — behind one alert fired
once. Fixed by bounding the SILENCE, never by retrying: a retry against
`NEVER_WORKED`/`UNRESOLVED` is the exact double-close the market-crossing fix above
exists to prevent. A repeating `_SPENT` escalation now pages every
`watchdog.exit_unattempted_max_s` for as long as the position stays unresolved and
held, reusing the existing key rather than adding one. That closed the phone side
and left the page rendering the same position as ordinary and open — "Exit
triggers: all evaluable," "Open positions: 2 legs" — because the position had
simply been popped out of `_impaired` with nowhere else to go. A new live-read
field, `PositionWatchdog.spent_exit_attempts()`, closes that too: driven by the
scan and filtered by `_attempted` (never the reverse, so a closed position's row
clears rather than becoming a process-lifetime tally), rendered in both JSON and
HTML with the outcome, size, and duration named in words. No config key; `src/`
only.
→ [spent exit attempt](../decisions/2026-08-21-exit-attempt-spent-is-not-the-end.md),
[spent exits on /status](../decisions/2026-08-21-a-spent-exit-attempt-is-visible-on-status.md)

**The phone-alert throttle folded a second open position's stop-out into the
first's suppressed count.** `SlackNotifier`'s 900s coalescing window was
calibrated (2026-08-05) against one condition flapping on a process-wide signal,
then keyed on `kind` alone for every caller — including the kinds where a repeat
inside the window is a *different position*: `watchdog_triggered`,
`watchdog_exit_filled`, and the new `_SPENT` page above. With
`max_concurrent_positions = 2`, both spreads on one underlying, and a shared
short-strike breach routinely triggering both at once, two correlated stop-outs is
this design's normal bad day, not a tail — and the second one arrived as a bare
`(+1 suppressed)` up to fifteen minutes late. Every suppressed alert was still
Tier 1 in the audit log and unthrottled in the journal throughout — a
notification-latency defect, never a record one. Fixed by keying the throttle on
`(kind, scope)`, scope read from the payload's `candidate_id` (falling back to
`external_identifier`); a kind naming no subject behaves exactly as before. Two
watchdog payloads had to start carrying `candidate_id` at the top level rather than
only nested inside `position` for the scope reader to see it. No config key, no
`AlertFn` signature change; `src/` only.
→ [alert throttle](../decisions/2026-08-21-alert-throttle-is-per-position.md)

## Deferred

**A confirmation-gated exit re-attempt.** The spent-exit fix above bounds the
silence; it leaves the one-attempt rule absolute. `_await_settled` already
produces the positive confirmation a safe second attempt would need, and the six
spent outcomes split cleanly — some (`CROSS_UNPRICEABLE`) are structurally the same
"no order exists" case a retry already handles safely elsewhere, others
(`BLOCKED`, `CANCELLED_ELSEWHERE`) must never retry. Real today, but it is a change
to a stated non-negotiable, needs a per-outcome taxonomy rather than a uniform
rule, and needs sandbox exercise of paths CLAUDE.md still lists as NOT YET
EXERCISED (rejections, `Cancel Requested` going terminal). Open decision, not a
bug.

**`/status` naming an UNWATCHABLE position.** `scan.unattributed` / `scan.malformed`
— a held position Argus's own two records cannot turn into a watchable spread, so
no virtual stop is evaluated for it — pages Tier 1 once per episode and appears
nowhere on the page: its legs show under "Open positions" with nothing marking
them unwatched, and an already-impaired position vanishes from "Exit triggers" the
moment it drops out of the scan. The third instance of the same pattern the two
fixes above close (a page that reads calm for a position in the worst state the
system can put one in). Deliberately not folded into the spent-exit-attempts fix —
it wants the still-unbuilt `degraded_positions` proposal, one decision about what
the page owes for held-but-unmanaged positions generally, not a third one-off row.

**Moving the REST confirm entirely off `check_once`.** A4's fix bounds the blind
window's duration and A4b bounds how many there are; neither removes the fact that
the confirm is awaited inside the evaluation pass at all. Flagged during this work
as a bigger redesign than the finding's own evidence supported — the three gates
already in front of the round trip (refresh-due, `booked_but_absent` never
consulting it, closing-fill coverage) mean an ordinary session costs zero round
trips, which is why this stayed a latent-hazard finding rather than a live
incident.

**Whether a same-day restart re-arming the kill switch is acceptable.** Raised by
the daily-loss-breaker restart work as the adjacent, larger finding: the switch
holds no persistence of any kind (`KillSwitch.__init__` sets `_engaged = False`
unconditionally), and `/status`'s `kill_switch.since` is a durable audit *row*, not
durable *state* — the same distinction the breaker bug turned on. Not new to this
release; carried forward because it needs its own decision (the switch is
process-lifetime with no day boundary, so "rehydrate it" has to answer
day-bounded / never / manual re-arm — a question the breaker did not have).

## Methodology

**Three of eleven resolved items here were invisible to the proactive review that
found the other eight, and surfaced only once a sibling fix's own test was being
written:**

- **A3b** (the partial-answer route to the same double-close) was found writing
  A3's test — the empty-answer fix alone did not cover a broker answer that names
  only a walk's already-abandoned rungs.
- **A4b** (the per-shape, expiring cache) was found tracing A4's residual — A4
  bounded one blind window's duration; nothing yet bounded how many of them a
  churning account cache could produce.
- **A2b** (`/status` visibility for a spent exit attempt) was found as A2's own
  recorded residual — A2 bounded the phone-side silence and left the page
  rendering the same position as ordinary and open.

**For whoever runs the next proactive pass:** a read-only review finds one layer of
a defect class. Writing the test for a fix in that class can find a deeper one —
worth planning time for, not a mandate to re-scope the review itself.

## Deploy

Rebuild plus config, moving together, same pattern as v0.3.6.

```bash
cd /opt/argus
git fetch --tags
git checkout v0.3.7
git describe --tags && git status --short
sudo docker compose build
sudo docker tag argus:local argus:v0.3.7    # or the rollback below has no target
sudo systemctl restart argus.service
```

**The two halves are not independently safe:**

- **New image + old config → hard refusal at startup**, `ConfigError`:
  `missing required config key: watchdog.book_confirm_ttl_s`. Fail-closed and
  loud, which is the good failure.
- **Old image + new config → runs, silently unfixed.** The pre-v0.3.7 loader
  ignores the unknown key rather than rejecting it, so nothing announces that the
  per-shape confirm cache is not active. Rolling back the image alone leaves
  exactly this.

A full rollback needs both halves — `git checkout v0.3.6` for code and config,
`ARGUS_IMAGE_TAG=<v0.3.6 image>` in `.env` for the image.

**No dependency change** — `requirements.txt` is untouched and the
`--require-hashes` build is unaffected.

**This release touches live paths directly**, same as v0.3.6: `argus.toml` carries
`environment = "sandbox"` with `dry_run_submissions = false`, and every fix above
except A1 sits on the exit/watchdog/reconciliation path that already routes real
orders against cert. Confirm the deployed config still matches before restarting.

## Scope

**Three items are explicitly pre-live-min-size blockers**, per their own decision
records: the daily-loss-breaker restart bug (cert cannot exercise it — the
mutation-tested test is its only coverage before real capital is at risk), the
unmappable-orders reconciliation gap (the one rail whose whole premise is refusing
to resume on anything unexplained), and the entry-leg freshness gate (at
live-min-size these are the quotes real capital is priced off). None of the three
is validated by more sandbox time; they are validated by the tests already
described in their own records.

**The daily max-loss breaker remains structurally inert in sandbox**, unchanged by
this release — day P&L is derived from NLV and cert never marks NLV, so "breaker
not tripped" here is not evidence the rail works. Proving it is a live-flip gate
this release does not close.

**Nothing here has been exercised in live fire as a set.** The correlated
double-stop-out B1 fixes for is argued from configuration and trigger shapes
(sandbox has never produced two simultaneous stop-outs); the spent-exit and
book-confirm-cache mechanisms are tested against fake clocks and real wall time in
isolation, not against each other under a real multi-position session. What is
measured is the mechanism, in tests — not yet the interaction, in production.
