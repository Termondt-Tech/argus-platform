*A verdict is only as good as the evidence it could actually reach, and the backup
check was reaching a conclusion from evidence it never had. `journalctl` does not
fail loudly for a caller who cannot read the system journal — it hands back
nothing — so an empty answer piped into `grep` was indistinguishable from "the NAS
never logged in". The producer arm needs no privilege at all, which is what made the
false verdict plausible rather than obviously broken: **snapshot fresh, NAS dead**,
stated with total confidence, on a healthy pull. Blindness is not silence, and the
one thing a backup alarm must never do is cry wolf convincingly.*

reserved for the live-min-size flip or a clean re-watch; **Rastaban** for

## Fixed

**An empty journal is not a silent NAS.** `argus-pull-check.sh` piped
`journalctl … 2>/dev/null` straight into the fingerprint `grep`, so a caller who
could not read the system journal got the same empty result as a caller who read it
and found no NAS logins. The system journal needs root; the producer arm (an `ls`
and a `stat` on a world-readable directory) needs nothing. So a hand-run without
`sudo` reported the most believable wrong thing available — a fresh snapshot and a
dead pull — and a false alarm on a backup rail is how a true one gets ignored six
weeks later.

Two blind branches now abort as **BROKEN** before the grep can turn silence into a
finding: a failed query, and an **entirely empty** ssh journal. The second is the
one that catches the unprivileged run, because `journalctl` commonly exits 0 while
showing such a caller nothing. Treating an empty ssh journal as *blind* rather than
*quiet* is safe by construction here — the droplet is internet-facing with fail2ban
watching and the NAS itself authenticates every 6h, so a genuinely silent 48h window
does not occur, and refusing is the fail-closed direction regardless.

This is **2026-08-21's rule on a second surface**: *an empty answer is not a
verdict.* Absence of evidence that could not have been collected says nothing, and
"cannot tell" must never render as a finding — the same reason an unreadable public
key already aborted rather than passing. The producer arm was written that way and
the consumer arm was not, in the same file, on the same afternoon.

Deliberately **not** matched on `journalctl`'s prose (`No journal files were
found`). That is the `Order.reject_reason` rule: branch on the mechanism, never on
a message another program is free to reword.

**Snapshot retention is not cheap, and `KEEP` counts files rather than days.** The
rotation comment claimed *"~7 MB each, so retention is cheap"* — it had taken
README's "~7 MB per full session", a **growth rate**, and applied it to a snapshot,
which is a complete copy of the whole DB. Measured on the droplet 2026-09-06:
**490 MB at 688,265 records**, so the default `ARGUS_BACKUP_KEEP=14` is **~6.9 GB**
standing, and it tracks the DB rather than the day's activity — roughly **32 GB a
year out** at README's own ~1.8 GB/year. Corrected, with a pointer to `df -h` and to
the still-open droplet disk-headroom item in `go-live-findings.md`.

And because nothing is keyed to the trading date, **N runs in one day evict N days
off the back.** Verifying the v0.3.20 deploy by hand rotated out three. That was
safe only because the NAS pulls every 6h and had already collected them — which is
exactly what is *not* true on a day the pull is broken, the day someone is most
likely to be running it by hand, and the day the runbook now tells them to. Both
manual-run sites say so, and every run ends with `retaining N/14 snapshots, <size>
total`, because a number nobody prints is a number nobody notices until the disk is
full.

**`--dry-run` cannot show a release its own plan, and v0.3.20's notes claimed it
could.** The hand-over is gated on the checkout and `--dry-run`'s whole contract is
that nothing is checked out — in v0.3.19's script the dry-run exits at line 291, the
checkout is at 313, the hand-over at 342. So a release that ships a different deploy
script always dry-runs under the **old** one. Observed live: v0.3.20's dry-run
printed v0.3.19's `checkout + restart only`, a restart that then correctly did not
happen. The notes told the operator to expect an `ancillary units CHANGED` block
where it structurally cannot appear, and to expect a restart verdict the hand-over
reverses. Corrected in `v0.3.20.md`, with both plans and which one governs stated
explicitly.

**The NAS cannot use a Tailscale address, and the script's own comment said it
could.** `DROPLET_HOST` carried `# or the droplet's Tailscale 100.x address`;
Tailscale is not installed on that device and a conventional install would not
survive it — `/` is a RAM disk rebuilt from the firmware image at every boot, the
same structural reason the crontab does not persist. It costs nothing, because the
network path was never the security boundary: the rrsync restriction on the droplet
side is, and it holds regardless of how the packet arrives. Comment and runbook now
say so, with the confirmed public IP.

**Smaller, from the same session:** `systemctl status` exits **3** on a
correctly-finished `Type=oneshot` unit — `inactive (dead)` *is* the success state —
so the runbook and the v0.3.20 deploy steps no longer chain anything off it with
`&&`. And `journalctl` needs `sudo` on the droplet, per the standing sudo boundary;
the documented commands now say so.

## Added

`tests/test_deploy_wiring.py` gains
`test_the_backup_check_never_reports_a_verdict_it_could_not_have_reached`. It pins
that the query's failure is branched on rather than swallowed, that an empty journal
aborts, that **both** blind branches sit above the fingerprint grep (below it they
would prove nothing), and that no assertion matches `journalctl`'s message text.

Its own first draft failed on its own comment — the file forbids matching that
prose, and the comment quotes the prose in order to forbid it. Asserted against
`_uncommented` source, which is the case this test file already exists to handle.
Mutation-checked both ways: swallowing the exit status and deleting the
empty-journal branch each fail it.

All five consumer-arm paths were exercised against a stubbed `journalctl` — query
failure, exit-0-with-no-output (the unprivileged run), whitespace-only output, a
readable journal with no NAS login (a **true** silent NAS), and healthy. The first
three now report BROKEN and the fourth reports SILENT, which is the distinction the
release is for.

**A new tool, `argus.tools.regime`, reads the regime telemetry back — nothing
had, since it started being computed and logged 2026-08-12.** `signal/regime.py`
estimates `atm_iv`/`skew` on every tick and rides them on `signal.none` /
`signal.candidate`, specifically so `[regime]`'s thresholds could eventually be
fit to the *recorded* distribution rather than a guess. That distribution had
never been read. `tools.regime --config <profile> [--from D] [--to D] [--at
HH:MM]` is read-only (`mode=ro`, no lock, safe mid-session) and reports: which of
three NaN modes an unestimated reading fell into (`guard`, the arithmetic bound
below 10 minutes to settlement, working as designed; `no_strip`, a feed-coverage
gap; `negative`, a crossed or stale quote — three different problems the payload
already distinguishes with no code change); one reading per session at a **fixed
ET clock**, because the estimator is not scale-free in time-to-settlement and
pooling ticks fits the clock rather than the market; the distribution with
blackout sessions excluded by default, since the strategy refuses every entry on
them; and the decision rule, printed rather than applied — a human picks the
branch, the same discipline `tools.evaluability` already holds. Run against the
2026-09-07 droplet snapshot pulled to the NAS: 97.2% of 86,471 real readings
estimated, zero `negative` failures, and skew crossing zero *inside the entry
window* on 21 of 21 sessions — a clock artifact in the estimator's strip
composition, not a market effect, and the strongest reason `[regime]`'s side
gate stays unarmed. Full write-up:
[regime status](../../RESULTS.md),
[the first measurement](../../RESULTS.md).

**Realized volatility, beside the implied number it had nothing to compare
against.** The regime telemetry gave `atm_iv` — a level, and the read above
never asked whether that level was *rich*. `signal/realized.py` closes the
arithmetic half: pure, no I/O, no clock read, no config — the same contract
`compute_regime` holds and for the same reason. Close-to-close quadratic
variation over a fixed grid, annualized on `MINUTES_PER_YEAR` **imported from
`regime.py` and never redefined**, held by an AST test — two copies of an
annualization basis is how the one number anyone actually wants, IV/RV,
silently stops meaning anything. `tools.regime` now reports both together: RV
and IV/RV on the daily series, an aggregate (mean, terciles, `corr(atm_iv, RV)`
for forecast skill — measured **r = 0.84**, not mechanical, since implied comes
from the option chain and realized from the index path — and
`corr(atm_iv, IV/RV)` for whether the *level* predicts richness), and the
volatility signature plot that chose the 60-second grid — printed on every run,
not just once, because the flatness it shows (5s through 900s) is a property of
SPX being a *computed* index rather than a traded price, and a future change to
that should be visible rather than silently biasing the series.

**Nothing acts on it.** No gate input, no size input, no config key, no new
audit category — the `[regime]` pattern exactly: compute it, make it readable,
let a decision record cite a measured distribution before anything conditions
on it. `src/` and `tests/` only, so by the v0.3.20 classifier this is a
**no-restart** addition, folded into this release rather than shipped alone
only because it landed the same day as the NAS work.

**The window is a module constant and must never read `signal.entry_earliest`**,
even though the two hold the same value today — that key is config and can
move, and the series would silently redefine itself with nothing saying so. Held
by an AST test asserting the module imports nothing from `argus.config` at all,
so the comment explaining the rule cannot itself trip a naive text-match version
of the same test.

**A short or gappy session reports no number, with the reason — and the
reason it needs two, not one, showed up on the first real run.**
`span_too_short` catches a path that does not cover the window (a late start, a
process that never came up); `coverage_too_low` catches holes *within* a span
that looks complete. Backfilling 2026-08-05 .. 2026-09-03 against
[the 2026-09-08 measurement](../../RESULTS.md)

Gated, the finding strengthens across the board (IV/RV mean 1.182 → **1.215**,

multiplier — does: `corr(atm_iv, IV/RV)`'s 95% bootstrap CI is
**[−0.69, +0.12]**, spanning zero, terciles still 1.29 / 1.19 / 1.19.

## Promoted

**P5's cancel recheck now actually cancels, in cert.**
`watchdog.unmanaged_order_cancel` moves `false` → `true` in `argus.sandbox.toml`
alone. dev and live stay `false`, for different reasons: dev routes nothing so it
registers no residuals at all and the flag is moot there; live stays
`would_cancel` because **inheriting `true` at the cutover would be the first fire
of an unproven path on the day of the first real order** (F2 from the
config-profiles design, D6). This is the promotion the module has been waiting for
since v0.3.13 shipped it on 2026-08-30.

**What changes is one call, and nothing else.** The flag gates exactly one outbound
`cancel` in `execution/residual_orders.py`, and a structural test asserts there is
exactly one such call and that it sits inside exactly one `_cancel_enabled` branch.
Everything upstream ran identically in `would_cancel` mode and is unchanged:
registration at `PriceWalkingLoop._finish`, the recheck stepping on P4's existing
`get_live_orders()` poll (still zero extra broker requests), `read_sighting`'s
six-value state table, the settle allowance, `cancel_licence`'s OPEN/CLOSE split
with the `minted_direction` ↔ `parse_external_identifier` cross-check, the
geometric backoff, and the `_Escalation` page. **An OPENING order is still all that
is ever cancelled**; a closing one is paged and never touched, under any halt or
grade, because cancelling a close strands a position.

**What the stage proved, and what it structurally could not.** `would_cancel` ran
from 2026-08-30 and validated the inputs on real cert data: on 2026-09-01
`put-7600-7595`'s walk finished `UNRESOLVED` on a cert read timeout, `_finish`
registered the abandoned order, the watchdog's next poll saw it **FILLED**, and the
position was adopted, watched and flattened at 15:31 — the whole arc end to end,
with `minted_direction` read correctly on an opening fill. What it never exercised
is the WORKING-past-allowance branch itself, because most residuals resolve on the
first poll or two. **No `order.residual_would_cancel` record has ever been
observed.** That is exactly the distribution the design predicted, and the design
said so in advance: *"expect it to validate the inputs thoroughly and the decision
almost never, and size the stage accordingly — a week, not a month, and do not wait
for a `would_cancel` record to appear before promoting."* Nine days.

**So the first fire will be the first fire**, and the blast radius is bounded by
construction rather than by evidence: a cancel is monotone toward less exposure —
it cannot create a position and cannot increase size — it is opening-orders-only,
and it is bounded on RATE, not count, at `unmanaged_order_max_s` (900s, unchanged
and already deployed since v0.3.13). At that floor a four-hour stuck order costs
~30 cancel requests across a whole session, against a documented ceiling of 40 per
*second* with `ratelimit.py`'s process-wide governor underneath.

**Confirm it live on `/status`, not in the config.** The `unmanaged` section's
residual row carries the mode on its summary line and must now read `cancel` where
it read `would_cancel`. That row was built for this moment (2026-09-02): the flip
carries no code, so the page is the only surface that shows which mode is actually
loaded.

**Two tests changed, both deliberately.** `test_the_shipped_configs_carry_the_key`
asserted `False` across all three profiles with a comment saying *"flipping cert is
meant to break this line: a rail changing state should cost an explicit edit"* — it
now pins the three profiles separately, so promoting **live** costs its own edit.
And the sandbox↔live divergence allowlist in `tests/test_config_profiles.py` gains
the key with its reason; that pair count goes 3 → 4, still under the base+overlay
revisit threshold of 10.

**Known blind spot, unchanged and worth watching after the flip.** One failed
`get_live_orders()` poll blinds P4's count *and* this recheck — 66 such ticks on
2026-09-01 — and the recheck's rate bound is measured against ticks that happen.
Absence is still never a verdict in either direction, so the failure mode is a
cancel that arrives later than the backoff implies, never one aimed at the wrong
order. The registry also still **never rehydrates**: P5 prevents 2026-08-28's state
from arising and does not resolve a previous process's orphan after a restart.

[config profiles](../decisions/2026-09-04-config-profiles.md)

time, so there is still no `sudo cp` step and nothing to `daemon-reload` — but

change `argus-deploy.sh`, so there is no hand-over and the plan prints **once** —
the opposite of v0.3.20, and the reason its dry-run is trustworthy where v0.3.20's
was not.

### THE NAS-SIDE STEP v0.3.20 NEVER APPLIED — do this one

**v0.3.20 hardened `scripts/argus-pull.sh` and `scripts/argus-pull-watchdog.sh`,
and shipped them nowhere.** Those two run on the **NAS**, at
`/path/to/nas/argus-pull/` — a third machine. `argus-deploy.sh` touches the
droplet only, no systemd unit references them, and the classifier calls `scripts/`
inert, which is **correct about the container and silent about the NAS**. So they
are sitting in the droplet's checkout, unused, and the NAS is still running the
pre-v0.3.20 copies: `kill -0` with no `cmdline` confirmation, `known_hosts` on the
RAM disk, and an `@reboot` entry that can fire before its own path is mounted.

This is the ancillary-units finding **one host further out**, and it is not covered
by any check yet. From your laptop (runbook §13 has the full context):

```bash
scp scripts/argus-pull.sh scripts/argus-pull-watchdog.sh scripts/argus-pull-daemon.sh <nas-user>@<nas-ip>:/path/to/nas/argus-pull/
```

**The daemon does NOT need restarting, and restarting it wrongly is the bigger
risk.** Only `argus-pull.sh` and `argus-pull-watchdog.sh` changed;
`argus-pull-daemon.sh` is byte-identical. The daemon re-invokes
`sh .../argus-pull.sh` on every loop iteration and cron re-invokes the watchdog
every 15 minutes, so both changed files are read fresh from disk — the new copies
are live at the next pull (≤6h) and the next `*/15` tick. The only script the
running process holds in memory is its own, and that one did not change.

**Do NOT `rm daemon.pid` while the daemon is alive.** The watchdog treats a missing
pidfile as "not running" and `nohup`s a second daemon while the first keeps going —
two daemons, with the new one owning the pidfile so the old is no longer reachable
through it. The `rm` belongs only to the post-reboot recovery case, where the pid is
stale. Check first:

```bash
ps | grep argus-pull-daemon    # alive? then leave the pidfile alone
```

Two things the `scp` itself changes, both of which fail silently:

```bash
ls -l /path/to/nas/argus-pull/*.sh
```

**`argus-pull-watchdog.sh` and `argus-pull-daemon.sh` are mode 644 in git** (only
`argus-pull.sh` is 755), and cron invokes the watchdog **directly** rather than
through `sh`. If the copy carried the source mode across, cron can no longer run it
and the daemon has lost its only recovery mechanism — with nothing to say so until
the next time it was needed:

```bash
chmod +x /path/to/nas/argus-pull/*.sh
```

And the copy overwrote `DROPLET_HOST` / `DROPLET_KEY` with whatever the repo
carries. Confirm they still name this droplet and this key:

```bash
grep -n 'DROPLET_HOST=\|DROPLET_KEY=' /path/to/nas/argus-pull/argus-pull.sh
```

Confirm the crontab still holds the one `*/15` line and that no `@reboot` line
survives:

```bash
crontab -l | grep argus
```

**Empty output is a live gap, not a pass — and it was empty when this was run on
2026-09-06.** The daemon was up and pulling, so backups were flowing, but the
watchdog was not scheduled: nothing would have restarted the daemon if it died.
That is the 2026-08-09 state minus the death. Confirm the pidfile matches the live
process first (so the watchdog cannot spawn a second daemon), then append —
never rewrite, this device runs its own WD jobs in the same crontab:

```bash
cat /path/to/nas/argus-pull/daemon.pid; ps | grep argus-pull-daemon
```

```bash
crontab -l > /tmp/ct && printf '*/15 * * * * /path/to/nas/argus-pull/argus-pull-watchdog.sh\n' >> /tmp/ct && crontab /tmp/ct && crontab -l | grep argus
```

`watchdog.log` staying silent afterwards is success — it logs only when it *starts*
something. **This step is manual after every power event and always will be**; the
droplet-side check bounds the exposure to 48h, it cannot restore the entry.

Then watch the next pull actually use the new script — it writes `known_hosts` on
the persistent partition for the first time, so the file appearing there is the fix
working:

```bash
tail -20 /path/to/nas/argus-pull/pull.log && ls -l /path/to/nas/argus-pull/known_hosts
```

### Rollback

`scripts/argus-deploy.sh v0.3.20` — **not** a bare `git checkout` this time. The
config is bind-mounted and is read once at startup, so rolling the tree back
without a restart leaves the promoted flag live in the running process; and the
image moved, so the checkout alone would leave v0.3.21's image attached to
v0.3.20's tree. Re-deploying the older tag restarts unconditionally and both
read-backs assert the result. The NAS copies are **not** rolled back by any of it —
they are on another machine and were never versioned by this deploy, which is the
gap named above.

**Rolling back the flip alone** is a one-line edit to `argus.sandbox.toml` plus a
restart, and it is the safe direction: `false` is `would_cancel`, the same registry
and the same decision with the call not made.

## Scope

Four threads now, and only the first two share a cause. **Fallout from deploying
v0.3.20**: a check that could report what it had not seen, and a retention comment
that was wrong by roughly seventy times. **Planned work that landed alongside
it**: the regime/realized-vol instrument, and the cert promotion of
`unmanaged_order_cancel` — step 3 of the config-profiles migration, arriving here
rather than as its own config-only release. The release is named for the first
thread; the promotion is the one with a live rail on the other end of it.

**Owed, and not in this release.** Nothing verifies that a repo file whose
deployment target is the **NAS** ever reaches it. `test_deploy_wiring.py` now pins
the container's view and the ancillary host units; the third host has no equivalent,
and the failure is silent in exactly the way the other two were before they were
pinned — the release deploys green and the change does not exist where it runs. The
NAS-pull check would catch a *consequence* eventually, but only if the un-applied
change was itself the fix for an outage. Worth a mechanism, not just this paragraph.

**Owed, and now one step closer.** Step 4 — the live cutover — is the next
config-profiles step, and it is now also the first deploy on which the fingerprint
read-back stands alone. See the note under the header.
