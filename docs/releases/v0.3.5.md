# v0.3.5 — Alcor

*80 Ursae Majoris — not an eye, but the classic **test** of one: splitting Alcor
from Mizar was the ancient eyesight check. This release found the watchman's own
eye reporting a position that was not there, and gave it a way to check itself
against an authority.*

> Spends the stretch the pool flagged. Alcor qualifies by tradition rather than
> etymology, which the naming rule permits but marks — see
> [releases/README.md](README.md#release-names--arguss-eyes).

**Requires an image rebuild AND a config change, and they must deploy together.**
This is a `src/` release, and it adds a REQUIRED key —
`[staleness] account_position_evict_after_s`. The v0.3.5 image against a
pre-v0.3.5 `argus.toml` refuses to start with
`missing required config key: staleness.account_position_evict_after_s`. The first
release since chunk 5 for which that corollary bites; see **Deploy** below.

## Fixed

**The "broker-derived" open-leg count was a mirror that could drift, and it paged
the one watchdog condition deliberately built to have no settle allowance.**

Found at an intraday checkpoint on 2026-08-19. `/status` reported
`open_position_count: 3` against `max_concurrent_positions = 2`, so
`open_spread_equivalent` sat exactly at the cap and every candidate in the recent
tail was denied `concurrent_limit`. The watchdog carried a standing
`held_but_unbooked` disagreement — broker 3 legs, ledger 2 — which had paged once
and then written 266 Tier 2 repeats, roughly 66 minutes at the 15s refresh cadence.

`tools.account` against cert said otherwise. REST held **two** legs, exactly the
spread the watchdog was watching:

```
SPXW  260819P07685000  signed_qty=-2
SPXW  260819P07680000  signed_qty=2
```

There was no third leg and no unwatched position. The day's own records agreed —
2 entries plus 1 watchdog exit, 3 orders, 6 fills, 2 legs held.

**Mechanism.** `AccountStateCache` had one eviction path: a `CurrentPosition` event
carrying quantity zero. `seed()`, the "authoritative REST snapshot", wrote every row
it was handed and subtracted nothing. The false premise is that a closed position
arrives as a zero row — it does not, the REST endpoint simply omits it. So a close
event lost during a stream outage (`account.refresh_failed: 53` across
`account.refresh_recovered: 22` episodes that session) left an entry **nothing could
remove**: the liveness refresh re-seeded every 10s for over an hour, refreshing the
two real legs and stepping past the ghost each time.

**Fixed** — `AccountStateCache.evict_absent` subtracts what a successful, complete
REST fetch did not report, and `seed()` calls it. A failed or partial fetch never
reaches eviction; the cache is left untouched so a broken link keeps looking broken.

**The eviction is AGE-GATED, and that is the whole safety argument.** Evicting on
absence alone fails in the direction that matters: the broker's book trails a fill
by ~4-5s, so a snapshot taken inside that window legitimately omits a position that
really is held, and dropping it would under-count open spreads and release a
concurrent slot already spoken for. The two cases separate cleanly on age — a real
position is in every snapshot and is re-touched by every seed, a ghost is in none
and climbs without bound.

**The no-allowance page now confirms against REST before it fires.**
`PositionWatchdog._cache_is_over_reporting` runs one `fetch_positions()` round trip
before `held_but_unbooked` pages. REST backing the LEDGER means the cache invented
the leg — Tier 1 `watchdog.book_cache_over_reporting`, no alert. REST backing the
CACHE means a real position is unbooked — pages exactly as before. Three properties
are load-bearing and tested: every failure path pages (a confirm that raises, times
out, or returns None never suppresses), the escalation edge is not consumed so a
suppressed episode that turns real can still page, and it is one round trip per
distinct `(broker, ledger)` shape rather than one per tick. `booked_but_absent` does
not consult it — that direction already has a settle allowance.

**Two docstrings that encoded the false premise are corrected.**
`RiskSnapshot.open_position_count` claimed to be broker-derived, and that claim is
the entire safety argument for preferring it over the ledger;
`session._broker_position_count` went further and named the REST re-seed as what
made it trustworthy. Both now say mirror, and state the bound on the drift.

→ [ghost positions in the account cache](../decisions/2026-08-19-account-cache-ghost-positions.md)

**`/status` went blank on the day's activity at the close.** `session_counts` — the
field v0.3.4 added precisely so the phone-reachable surface could answer "has
anything executed today?" — was cleared by `session_finished` along with the live
risk and link sources. Caught at the 16:41 ET EOD read on 2026-08-19: it reported
the day's tally all afternoon and then `{}` forty minutes after the close, which is
exactly when it gets looked at.

The clear was inherited, not decided. `session_finished` clears the live sources
because they are handles into a feed that no longer exists, and the
[monitoring-surface record](../decisions/monitoring-surface.md) justifies that in
terms of **ages** reading "no active session" between days. The counts baseline is
not a handle — it is a static integer snapshot, and the totals it subtracts from are
read out of the audit DB, which is still there and still correct.

**Fixed** — the baseline now survives session end and is replaced by
`session_starting`. Between the close and the next morning, `session_counts` reports
the session that just ended, paired with the `trading_date` that labels it. The live
sources still read `null`; that asymmetry is the point, and a test asserts both
halves.

**`tools.mark`'s settlement tally read as "no losers" on a day that had one.** The
2026-08-19 EOD run printed, verbatim:

```
2 idea(s), 1 win / 1 loss, total P&L -0.00
full credit 2  partial 0  max loss 0
```

Both lines are correct and they answer different questions, which is exactly the
problem. `Outcome.result` is settlement-derived for **every** row — `full_credit`
means the index settled beyond the short strike — so for an idea closed intraday it
is a **counterfactual**: settlement is not what governed its P&L. The call spread
was stopped out at 2x credit for −120 on a day it would have expired worthless.
`outcome.py` states the distinction plainly (`result` = where the index settled,
`shape` = whether that settlement governs); the summary printer just never said
which of the two it was reporting.

**Fixed** — the tally is labelled `where the index settled:` and, when any row in it
closed before 16:00, discloses how many and that settlement did not govern their
P&L. No scoring changed; the realized figure and the stop's bill below it were
already right. The disclosure is conditional, so it cannot become boilerplate that
gets skimmed past on the days it matters.

## Added

**`[staleness] account_position_evict_after_s`, `60.0`.** How stale a cached
position absent from every REST snapshot must go before the re-seed drops it. ~12x
the propagation lag and 6x the refresh interval.

The loader **refuses** a value at or below `account_refresh_s`: below that a real
position can age out between two seeds and be evicted on timing jitter, which is the
direction that fails open. Enforced, not documented.

It is deliberately **not** a reuse of `watchdog.book_settle_s`. Both are sized
against the same propagation lag, which is exactly why sharing one number would weld
two unrelated conditions together — the same reasoning `tools/evaluability.py`
records for the blind-episode allowance. Move one, and the other is unaffected.

**The `[audit] synchronous` write-rate basis gains its second post-Fix-C
measurement** — 1.52/s total, 0.25/s Tier 1 on 2026-08-19, against 2.33/s and
0.20/s on 2026-08-18, both over 6.33h. The comment now warns **not to read the two
as a trend**: the rate scales with POSITIONS WATCHED, not with time, because
`watchdog.check` is per position per tick and dominates the total. 2026-08-19 came
in lower purely because the stale-cache phantom pinned the concurrent limit and only
one position was watched for most of the day. Two positions all session is what to
size against, so 2.33/s stands as the honest high-water mark. Comment-only.

**`account.position_evicted` telemetry**, carrying the age each entry reached. That
is the measurement the threshold gets re-tuned from, the discipline `book_settle_s`
was sized under. **A healthy session evicts NOTHING** — the stream's zero-quantity
frames arrive and clear positions first — so the RATE is the signal: sustained
evictions mean the account stream is dropping events.

## Deploy

Rebuild plus config, moving together. The tag carries both.

```
cd /opt/argus
git fetch --tags
git checkout v0.3.5
git describe --tags && git status --short
sudo docker compose build
sudo docker tag argus:local argus:v0.3.5    # or the rollback below has no target
sudo systemctl restart argus.service
```

**That tag step is not optional and was missing from every deploy before this one.**
`docker compose build` writes `argus:local` and nothing else, so each build
overwrites the previous release's image in place — `sudo docker images argus` on the
droplet returned exactly one row on 2026-08-19, meaning the `ARGUS_IMAGE_TAG` half
of the documented rollback had never once been available. v0.3.4's image is gone;
it is reproducible from its git tag (deterministic build) but not at incident speed.

**The two halves are not independently safe:**

- **New image + old config → hard refusal at startup**, `ConfigError`. Fail-closed
  and loud, which is the good failure.
- **Old image + new config → runs, silently unfixed.** The pre-v0.3.5 loader
  ignores the unknown key rather than rejecting it, so nothing announces that the
  eviction is not happening. Rolling back the image alone leaves exactly this.

A full rollback therefore needs both halves as usual — `git checkout v0.3.4` for
code and config, `ARGUS_IMAGE_TAG=<v0.3.4 image>` in `.env` for the image.

**No dependency change**, so `requirements.txt` is untouched and the
`--require-hashes` build is unaffected.

**This release does not clear a ghost already in a running process.** The eviction
runs on the next `seed()` after startup. A session carrying one at deploy time is
repaired by the restart itself.

## Not a defect

The broker's open prices for the held spread implied a net entry credit of
3.60 − 3.00 = 0.60, while the watchdog carried `entry_credit: 0.55`. Checked and
left alone: `entry_credit` is the filled opening order's LIMIT, not the realized
fill, documented in `execution/store.py` as at-worst-slightly-low — which makes the
2x trigger fire slightly EARLY. Safe direction.

> **Superseded 2026-08-20 — the dismissal above leaned on a word that was wrong.**
> This observation *is* the bias, at 9.1%, and a second measurement the next day put
> it at 18%. The DIRECTION is still safe and still not a defect; what does not hold
> is "slightly", and with it the reason to stop looking. `credit_stop =
> credit_multiple × entry_credit`, so the stop has been tight by the same margin —
> and **no conclusion about `credit_multiple` may be drawn from a dataset measured
> against this basis.** Left in place as the record of what was known on 2026-08-19;
> the corrected statement is in `execution/store.py`'s `OpenSpread` docstring.

## Scope

Not sandbox-specific; the mechanism is identical in live. **Not a live-flip gate** —
a ghost inflates the count, so the concurrent limit errs closed, and startup
reconciliation reads REST directly rather than the cache, so there was never a
false-halt path. The cost is lost trading days and a crying-wolf alert on the
highest-severity watchdog channel, which is why it lands before size is scaled.

The one live-flip gate is unchanged: the daily max-loss breaker remains structurally
inert in sandbox.
