# v0.3.17 — Alphard

*TAGGED AND DEPLOYED 2026-09-05. Prepared from what was on `main` since
`v0.3.16` (commits `d3ce6bd`, `12326cf`, `05239df`). Two unrelated additions, bundled
because that is what shipped since the last tag rather than because they share
a shape — the same honest framing v0.3.15 used for its `/status` work. The
headline is the second one: **the process no longer trusts a default it cannot
verify.** `ARGUS_ENV` used to override the `environment` key; now it names the
FILE, the key stays the sole authority on trading behaviour, and the loader
refuses when the two disagree. There is no default config path any more — a
bare `python -m argus` used to open `argus.toml`, which from the repo root is
the live database, and that default was literally the mechanism of the
2026-07-21 incident. And `/status` now carries a config fingerprint, because
the version stamp has always had a blind half: config is bind-mounted and
explicitly does not roll back with the image tag, so nothing before this could
say which config bytes a config-only release actually loaded.*

*Named per the Argus's Eyes convention (`docs/releases/README.md`). The pool
is down to **Aldebaran** (reserved for the live-min-size flip or a genuinely
uneventful week) and **Rastaban** (reserved for dual-watchdog / consensus
verification) — neither fits, so the name is found outside the table, the
same pattern as Alterf, Polaris, Oculus, Albireo, Eltanin, Grumium and
Alsciaukat. **Alphard** — α Hydrae, Arabic *al-fard*, "the Solitary One" — is
Hydra's only bright star in a long, dim constellation, and it earns the name
literally: with nothing bright anywhere near it, it cannot be mistaken for
anything else in the sky. That is this release's whole mechanism. A config
file used to be identified by convention (its path, a variable that could
silently override what it said about itself); now it identifies itself —
named by its own filename, checked against its own `environment` key, and
fingerprinted by the sha of its own bytes — and cannot be confused with a
different file the way `argus.toml` could quietly be pointed at either
environment before. Qualifies by tradition rather than a literal "eye," the
same standing already granted to Alcor, Alterf, Grumium and Alsciaukat.
**Aldebaran and Rastaban stay reserved** — this is not a clean re-watch and it
adds no second verification loop; it makes the existing one unable to lie
about what it is looking at.*

**Mixed deploy. `05239df` is `src/` + config + tests, no new config KEY — the
image and the config files move together but nothing REQUIRED changed shape,
so an old config still loads under the new code. `d3ce6bd` is also `src/` +
data files, no config key.** Both need a rebuild; neither needs a coupled
config move. `config.py`, `status.py`, `app.py`, `__main__.py`, and all nine
`argus.tools.*` entry points change for the config work;
`tools/blackout_dates.py` changes for the discretionary-dates work.
`argus.toml` gains a header-comment rewrite and no key changes;
`argus.live.toml` is regenerated (see Added, below) and remains untracked
pending step 2 of the profile migration.

## Added

**Config is now selected by PROFILE, and there is no default path.**
`ARGUS_ENV` used to *override* the `environment` key (`config.py`'s old
`env_override` parameter) — a second, silent answer to "are we routing real
money?" that could disagree with the file it was pointed at. It now names the
FILE instead: `ARGUS_ENV=live` resolves to `argus.live.toml` (against
`ARGUS_CONFIG_DIR`, defaulting to the working directory), `ARGUS_CONFIG`
still names an explicit path and wins when both are set, and setting neither
is a `ConfigError` — there is deliberately no third option. **The file's own
`environment` key remains the sole authority** on trading behaviour, and the
loader now refuses to start when the filename's profile and the key
disagree, armed by the filename itself
(`argus.<profile>.toml`; `_check_profile` in `config.py`). A path with no
profile in its name — `argus.toml`, or an ad-hoc `--config /tmp/x.toml` — is
legal and asserts nothing, which is what let this ship one release ahead of
the file rename it is designed for; `/status` renders that state amber and
says the check is not armed, rather than reading as ordinary.

**The old override was fenced only by accident.** `ARGUS_ENV=live` against
today's `argus.toml` happened to refuse to start, but only because
`staleness.account_stream_max_age_s = 120 > 30` tripped the live ceiling —
and that 120 is a cert-only artifact (`/positions` timing out in cert) that
could legitimately drop at any time, at which point the fence would have
silently stopped existing. Removing the override removes the reliance on a
fence that was never built to be one.

**No default config path, in the app or in any tool.** `python -m argus` used
to fall back to `./argus.toml` — the mechanism of the 2026-07-21 incident,
where a bare invocation from the repo root opened the live database
alongside a running session, took three `seq` values, and wedged the audit
writer for ~80 minutes. It now raises `ConfigError` with no config selected.
All nine `argus.tools.*` entry points (`account`, `chain`, `desk`,
`evaluability`, `mark`, `order_smoke`, `quotes`, `shadow`, plus the
already-required `loop_lag`) now require `--config` explicitly — there was no
default left safe to keep. `README.md`'s command examples are updated to
match; anything copy-pasted from an older revision of that file will now fail
loudly with argparse's own "the following arguments are required" instead of
silently opening whatever `argus.toml` happens to be in the working
directory.

**`/status` and the startup log carry a config fingerprint — the version
stamp's other half.** `version` (`git describe`, baked in at image build
time) answers "which code is running?" and is read back from the journal on
every deploy. Nothing answered the same question about config, and config is
the half explicitly excluded from the image (`docker-compose.yml`: "config
does NOT roll back with the image tag" — it is bind-mounted). So after a
config-only release, these were indistinguishable: the new config loaded; the
restart happened before the checkout; the mount path drifted; somebody
hand-edited the droplet and it has not restarted since. `Config.load` now
attaches `ConfigSource(profile, filename, sha)` — sha256 over the file
**bytes**, 12 hex characters — surfaced in `/status`'s JSON (a `config` object
beside `version`) and HTML (a "Config" row under Build), and folded into the
existing startup line rather than a second one:

```
argus build v0.3.17 config live/argus.live.toml @35211ce0032a
```

**A hash, not a hand-bumped `[meta] release` string** — deliberately: it
cannot go stale, needs no REQUIRED key (so introducing it forced no coupled
deploy), cannot be forgotten at tag time, and answers *are the bytes I
deployed the bytes that are loaded?* rather than *did somebody remember to
bump it?* The colour rule matches `_version_cell`'s: the expected state (a
named profile, a sha) is plain text; a profile-less filename is amber, and it
says why.

**Three full config files, pinned by a test rather than a merge layer.**
`argus.toml`, `argus.dev.toml`, and `argus.live.toml` carry the same 82 leaf
keys — that was already true and is now enforced. Base+overlay was rejected:
it puts a merge step in front of a fail-closed loader, splits 82 keys of
load-bearing prose away from the values they justify, and would have bought
that at a divergence of three keys. `tests/test_config_profiles.py` instead
asserts identical key sets across all three files, that **every profile file
actually loads** through the real loader (catching a broken cross-key
constraint or a live-fence violation in the file that is not being run
today), that every value divergence sits on an explicit, reasoned allowlist,
and the live-specific invariants (durability, database isolation, the welded
`max_concurrent_positions × max_loss_per_position ≤ daily_max_loss`
inequality). The revisit threshold — reopen base+overlay if sandbox↔live
divergence passes ~10 keys — is asserted, not just written down. **Four of the
last five releases forced a coupled config move**; a REQUIRED key added to
two files and not the third used to be a `ConfigError` discovered only when
that third profile is the one being started — for the live file, that is a
process refusing to boot at 09:29 ET on cutover day. The test caught a real
undeclared divergence (`dev` vs `live` on `account_stream_max_age_s`) before
a human read it.

**`argus.live.toml` regenerated, closing a cutover blocker.** The
previously-untracked file existed but was not a usable live config:

- **Both files resolved `audit.db_path` to the same volume path
  (`/data/argus.db`, via the Dockerfile's `WORKDIR /data`).** Flipping to live
  would have opened the **cert database** — the hash chain continuing from
  sandbox rows, and `positions` (which reconciliation reads back as expected
  state) holding cert-era rows compared against the live account:
  `missing_at_broker` on day one, a process-wide hard halt in `live`, not a
  lenient abort. Fixed: `argus-live.db`. The cert file is deliberately left in
  place beside it so `tools.mark` / `tools.desk` keep reading the cert-era
  record.
- `unmanaged_order_cancel` was `true` in the live file — P5's re-cancel path,
  which has never fired in cert. Reset to `false`; it is promoted in cert
  first, as its own config-only release, before the first time it fires does
  so with real money on the same day as the first real order.
- The semantic diff between `argus.toml` and `argus.live.toml` is now exactly
  three keys: `environment`, `audit.db_path`, and
  `staleness.account_stream_max_age_s` (the live ceiling, 30.0, against
  cert's 120.0 cert-`/positions`-latency accommodation).

**`discretionary_blackout_dates.txt` — hand-maintained, optional entry
blackout dates alongside the FRED/FOMC-generated list.** Same one-ISO-date-
per-line format as `fomc_dates.txt`, merged in on every
`tools.blackout_dates` regeneration (new `--discretionary-file` and
`--add-discretionary YYYY-MM-DD` flags), and rendered as a `DISCRETIONARY`
section — deliberately last, so a regeneration with none queued renders
byte-identical to before this category existed. **Optional where FOMC/CPI/
NFP/PCE are not**: `_refuse_if_any_event_is_empty` deliberately excludes it,
because an empty discretionary list is the ordinary state (most days nobody
has declared a one-off avoidance) while an empty FOMC/CPI/NFP/PCE list is
always a broken query. `_summarize` prints it with neutral wording when
empty ("none queued") rather than the required events' alarmed "NONE — will
not cover," for the same reason. **Never repurpose `[calendar] holidays` for
this**: that list means the exchange is physically closed and drives session
scheduling and 0DTE expiry resolution; a discretionary date means "market's
open, we choose not to enter" and suppresses new entries only — anything
already open still gets its watchdog, virtual stops, and 15:30 flatten. Two
dates are queued as of this release (2026-11-27, 2026-12-24).

## Deploy

Rebuild, and read the plan before running it — this release changes how
`python -m argus` and every `argus.tools.*` invocation is started.

```bash
cd /opt/argus
git checkout v0.3.17
git status --short                          # must be clean (or the expected argus.toml edit)

sudo docker compose build --build-arg ARGUS_VERSION=$(git describe --tags --always --dirty)
sudo docker tag argus:local argus:v0.3.17
sudo docker images argus                    # confirm the version tag is there

sudo systemctl restart argus.service

# Confirm what is actually running — read BOTH; this release is the reason to.
sudo journalctl -u argus.service -n 50 | grep 'argus build'
curl -fsS -H "Authorization: Bearer $ARGUS_KILL_TOKEN" \
     http://<tailscale-ip>:8443/status | jq '{version, config}'
```

**Before restarting, confirm the compose environment still resolves a
config.** Step 1 of the profile migration (this release) does not yet change
`docker-compose.yml` or `argus.service` — the container still gets
`ARGUS_CONFIG: /etc/argus/argus.toml` exactly as before, so **no droplet-side
wiring change is required for this deploy**, and the container's own startup
is unaffected. This matters for anyone running `python -m argus` or a
`tools.*` command **by hand** on the droplet or a laptop outside compose: any
such invocation that relied on the old `argus.toml` default now needs
`ARGUS_ENV=<profile>` or `--config <path>` explicitly.

`scripts/argus-deploy.sh` is **unchanged by this release** — the plan
detection, the build-input list, and the version read-back all behave
exactly as they did for v0.3.16. Steps 2–4 of the config-profiles design
(the file rename, `EnvironmentFile=/etc/argus/host.env`, and the script
reading the config sha back after every restart) are staged and not part of
this release; until they ship, a config-only release still verifies nothing
beyond what it always has.

**Rollback is `git checkout v0.3.16`, image-only.** No config key changed
shape, so a prior image reads today's `argus.toml` / `argus.dev.toml`
unchanged; the only thing a rollback loses is the config fingerprint on
`/status` and the discretionary-dates generator flags, neither of which any
running code depends on.

**After deploy, what to look for:**

- `/status`'s new "Config" row and the startup log's `argus build:` line
  carrying `config -/argus.toml @<sha>`. The profile reads **`None`, not
  `sandbox`**: `docker-compose.yml` is unchanged by this release and still
  mounts the plain-named `argus.toml`, whose filename does not match
  `argus.<profile>.toml` — so the row legitimately renders amber, saying the
  profile/environment check is not armed. That is correct and expected until
  step 2 (the rename) ships; it is not a fault to chase on this deploy.
- No change in trading behaviour: the `environment` key still decides
  everything it always did, and no REQUIRED config key changed value or
  shape.
- A hand-run `python -m argus` (or any `argus.tools.*` command) with no
  `ARGUS_ENV` / `ARGUS_CONFIG` set now refuses immediately instead of opening
  whatever `argus.toml` is nearby — this is the intended behaviour change,
  not a regression, and it is the whole point of this release's first half.

## Scope

**Two unrelated additions since v0.3.16, not one shape:**

- The config-profile mechanism, the config fingerprint, the default-path
  removal, and the regenerated `argus.live.toml` — step 1 of 4 of
  [`docs/designs/2026-09-04-config-profiles-and-config-only-releases.md`](../designs/2026-09-04-config-profiles-and-config-only-releases.md),
  approved 2026-09-04 with all ten §9 decisions and no amendments.
  → [decision record](../decisions/2026-09-04-config-profiles.md)
- The discretionary blackout dates addition to `tools.blackout_dates`,
  unrelated to the above and carrying no decision record of its own — see
  `CLAUDE.md`'s file-structure note on `discretionary_blackout_dates.txt`.

**Deliberately NOT in this release, staged as steps 2–4 of the config-profiles
design:**

- The file rename (`argus.toml` → `argus.sandbox.toml`), `.gitignore`ing the
  old name, and the host wiring (`docker-compose.yml`'s `${ARGUS_ENV:?}`,
  `argus.service`'s `EnvironmentFile=/etc/argus/host.env`). Until this ships,
  the droplet's compose file continues to set `ARGUS_CONFIG` explicitly and
  none of this release's new refusal paths are reachable through the normal
  service start.
- `scripts/argus-deploy.sh` reading the config sha back after every restart.
  **A config-only release today still verifies nothing** — this release adds
  the fingerprint a script COULD read, not a script that reads it yet.
- The cert promotion of `unmanaged_order_cancel` (F2 from the design) — reset
  to `false` in the regenerated `argus.live.toml` here, but not yet flipped
  anywhere, and it is the first intended exercise of the config-only release
  path once step 2 lands.
- The live cutover itself.
- Cert risk sizing in `argus.live.toml` (`max_loss_per_position`,
  `max_concurrent_positions`, `daily_max_loss`) — inherited unchanged from
  `argus.toml`'s cert-era numbers (F3 from the design); the welded invariant
  holds, but these are cert's numbers and the next gate is live-**min**-size,
  not live-at-cert-size. Decided at that gate, not here.
- `argus.dev.toml`'s `signal.max_width` still contradicts its own in-file
  note about tracking `argus.toml`'s values (F5) — harmless, since dev
  submits nothing, and allowlisted with that reasoning in
  `tests/test_config_profiles.py` rather than left silent.
- **No config hot-reload, and none is planned.** A config release is still a
  restart: config is read once at startup, half of it into frozen objects at
  session build, and risk rails changing under a live position is strictly
  worse than a scheduled restart.

**The daily max-loss circuit breaker remains structurally inert in sandbox**,
unchanged by this release. Proving that rail out is still a live-flip gate.

**Test suite: 1984 passing, up from 1955 at v0.3.16** — 29 new tests: 16 in
the new `tests/test_config_profiles.py` (identical key sets, every profile
file loads through the real loader, the divergence allowlist, the live
invariants, the filename-profile assertion end to end via a mislabelled
temp file), 3 driving the config fingerprint through `StatusService` from a
real `Config.load("argus.live.toml")` to rendered JSON and HTML rather than a
hand-built snapshot (2026-09-02's `_SEAMS` lesson applied ahead of time — a
copy into a target with `None` defaults cannot fail loudly, so it has to be
pinned by driving real objects through), 4 rewritten in `tests/test_config.py`
replacing the old `env_override` semantics with the profile assertion, and 8
already landed in `tests/test_tools_blackout_dates.py` for the discretionary
dates work.
