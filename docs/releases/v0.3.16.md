# v0.3.16 — Alsciaukat

*TAGGED 2026-09-04 — this heading read "NOT YET TAGGED" until 2026-09-10; the tag
exists and six releases have shipped since. Prepared from what was on `main` at the
time (commits `408d009`,
`acd844d`, `ccd810a`). Three fixes, one shape: **Argus already had the right
answer and a downstream reader substituted a worse one.** The order ledger
inferred an exit's direction from leg actions the broker relabels, when Argus's
own minted identifier said `close` all along. The exit's duplicate guard let a
transport error out of a bare `await` into the watchdog's hard-halt region — a
GET, asked before anything was sent, killed the process — when two other call
sites had already been taught that "I could not ask" is an exception, never a
verdict. And a submit the venue refused outright was reported as `no_order_exists`
with `reject_reason: null`, while the exception saying exactly why sat in scope
and was thrown away. All three are the exit path finally applying a rule the
system had already written down somewhere else.*

*Named per the Argus's Eyes convention (`docs/releases/README.md`). The pool is
down to **Aldebaran** (reserved for the live-min-size flip or the first genuinely
uneventful week) and **Rastaban** (reserved for dual-watchdog / consensus
verification) — neither fits, so the name is found outside the table, the same
pattern as Alterf, Polaris, Oculus, Albireo, Eltanin and Grumium. **Alsciaukat** —
31 Lyncis, Arabic *al-shawkah*, "the thorn" — sits in **Lynx**, the constellation
Hevelius drew into the gap between Ursa Major and Auriga and named for the eyesight
it takes to see it: its stars are real and technically visible, and you need a
lynx's eyes to catch them. That is this release exactly — three small, sharp
corrections, each at a spot where the correct value was present (a minted
identifier, a typed exception, `exc` still in scope) and a reader looked straight
past it. Qualifies by constellation and tradition rather than "eye" etymology, the
same standing the README already grants Alcor and Alterf. **Aldebaran and Rastaban
stay reserved** — none of this is a clean steady re-watch, and none of it adds a
second verification loop.*

**`src/` only. No new config key, no migration, no new audit category — a
rebuild-only deploy, and the cleanest since v0.3.10.** v0.3.15 was uncoupled on
config but still carried migration 0005; this one moves nothing but the image.
`execution/models.py`, `execution/loop.py`, `execution/watchdog.py`,

## Fixed

**A relabelled closing leg wrote the order ledger as an OPEN — the exit-path
mirror of the 2026-08-25 entry-side fix, and mint over infer wherever an
identifier exists.** `infer_direction` (`execution/models.py`) derives an order's
direction from the leg actions the broker echoes back — *any opening leg wins* —
on the premise that *Argus never mixes opening and closing legs in one order*.
True of what Argus SENDS; false of what the broker RETURNS. tastytrade labels each
leg relative to THE ACCOUNT'S net position, so closing a spread whose long leg is
another live spread's short means selling to close a strike the account is net
FLAT on — which comes back `Sell to Open`, and `[Buy to Close, Sell to Open]`
infers **OPEN** for an order whose whole job is to close. **Observed live
2026-09-01, three times in one session** (an opening order's leg back as
`Sell to Close`, two closing orders' legs back as `Sell to Open`), and the ledger
read back on 2026-09-03: all three closing rows durably carry `direction = 'open'`,
wrong from the first write, because `ack_from_response` / `broker.replace`
re-attach `candidate_id` but never `direction`, and `_upsert_order`'s
`ON CONFLICT` clause never updates it. **Benign on a FULL close** (`_pair_spreads`
nets the legs and short-circuits before reading direction — which is why it stayed
latent). **On a PARTIAL close the mislabelled order becomes `head`, its negative
CLOSE limit fails `entry_credit <= 0`, and a live half-spread is reported
`malformed` instead of watched** — no triggers, no flatten, no `/status` row, one
page per episode. **Fixed**: `map_placed_order` takes `direction` from
`parse_external_identifier` when the order is Argus's own — `external_identifier`
is a field Argus MINTED and the broker echoes verbatim — with `infer_direction`
unchanged as the fallback for a foreign order, the case that rule was actually
written for. `PositionWatchdog.note_fills` decides "a leg our own close just took
flat" the same way, so a relabelled OPENING fill (seq 420587's shape — an
`argus-open-` identifier, a `Buy to Close` action, `position_after == 0`) buys no
`held_but_unbooked` suppression and pages as it always should have.
`working_orders.open_working_spread_equivalents` is fixed by construction (it
reads `Order.direction`) — docstring updated, no code change, regression-tested on
the real 1430448 shape through the mapper. A disagreement is **Tier 2 telemetry at
the write moment alone** (`order.direction_disagreement` from
`AuditedOrderExecution.submit` / `.replace`, deliberately NOT from the polling
`get_live_orders()` path; `watchdog.note_fills_disagreement` for the reverse) —
never a halt, never a raise, never Tier 1, feeds no rail, mutation-verified both
ways. **What was NOT changed**: no backfill of the three durable `dir=open` rows
(Richard's explicit call — the truth is at Tier 1 in `order.submit_attempt` three
seconds before `order.submitted` overwrites it, so the column is repairable from
the chain if ever wanted, and a backfill would open a second write path against a
first-write-wins table for a column nothing safety-critical reads); `direction`
stays INSERT-only, pinned by a first-write-wins test; `store._apply_position` /
`signed_leg_delta` (the already-shipped entry-side sign fix), `residual_orders`'s
`minted_direction`, and `_await_settled`'s FILLED-wide / settle-narrow split are
untouched; nothing besides `direction` in `map_placed_order` prefers the minted
value. **The relocation that came with it**: `parse_external_identifier` moved
`execution/build.py` → `execution/models.py` (beside `ORDER_ID_PREFIX` /
`is_argus_identifier`, which it already depended on) so the mapper can call it
without an import cycle; every importer re-pointed (`reconcile.py`, whose module
docstring no longer needs to justify importing `execution.build` at all;
`shadow/marker.py`; `execution/residual_orders.py`; `tests/test_order_build.py`).
**The PARTIAL-close precondition has still never fired** — every relabelling seen
so far, entry or exit, has been on a FULL open or close. This fix makes that case
safe when it arrives; it does not, and cannot, exercise it. **Closes the standing
open decision** "where should an order's direction come from" in
`docs/decisions/README.md`.
→ [a relabelled closing leg can record an exit as an entry](../decisions/2026-08-25-relabelled-closing-legs-open.md)

**The exit's duplicate guard let a cert 502 out of a bare `await` and into the
watchdog's hard-halt region — a GET, asked before anything was sent, killed the
process and took the watchdog with it.** v0.3.15's first live-fire day (2026-09-03)
traded normally into the window — 701 candidates, 7 `entry.finished` — then cert
began failing (7 of 10 submits refused). One spread was open:
`call-7725-7730`, 2 contracts, and at ~11:03 `credit_multiple` began holding at
`cost_to_close 1.65` against `credit_stop 1.40` — a real 0.25-wide breach, far
past `PRICE_EPSILON`. The exit calls the loop with `guard_first_submission=True`,
and the guard branch inside `run()` was a **bare await — no timeout, no retry** —
propagating by design into the watchdog's hard-halt region. At 11:04:05 ET
`DuplicateOrderGuard`'s `get_live_orders()` took a 502; uncaught, it became
`watchdog.fatal` → kill switch → `HaltGrade.ALL` → `request_stop()`.
`_halt_on_exception` sets the SHARED stop event, so what the halt actually took
was the WATCHDOG: the triggered spread lost its virtual stop, its mark, its
`/status` row and — the one that matters on 0DTE — its 15:30
`FLATTEN_BEFORE_CLOSE`, for the rest of expiry day, **while being perfectly
evaluable** (priced at 1.65 that same second). This is A2's shape at process
scope — *a monitor disabled by the failure of an action it requested*. **The third
instance of one class**; 2026-08-26 closed the other two (`reconcile._ask_broker`,
`entry._check_for_duplicate`), and `entry.py`'s own module docstring names this
exact configuration as wrong — but scoped the conclusion to the entry path, and
`guard_first_submission=True` has exactly ONE caller in `src/`, the exit. **The
same day ran the A/B**: 7 failed entry-guard round trips retired 2 trade ideas and
the day continued; 1 failed exit-guard round trip halted the process. **Fixed**:
`loop._ask_guard` — 3 attempts, 1s/2s backoff, each under the existing
`[execution] guard_timeout_s` — raises a **typed** `GuardUnreachable` (carrying
`attempts` and `last`) on a spent burst, which `ExitExecutor.close` catches and
turns into **`ExitOutcome.NOT_ATTEMPTED`**: nothing was sent, the position keeps
its one exit attempt AND its flatten override, the trigger stays latched, and the
next cadence tick rebuilds and asks again. **Six decisions inside that**: the
exception stays an exception (only its type and bound change — chunk 3's *"I could
not check" must never become a `WalkOutcome`* is untouched); `NOT_ATTEMPTED`, not
a new outcome or a new escalation tag (2026-09-02's rule verbatim — the allowance
asks exactly one question, *was anything sent*), a fourth SENTENCE joining three
construction refusals; **the bound is on RATE, not COUNT — the opposite of
`_EXIT_SEND_ATTEMPTS`** (a guard check is a GET and costs no submission; a count
would leave a position unmanaged at 15:30 for a broker that recovered at 15:00 —
this incident in a smaller box), with the rate held by `_exiting` (one episode per
position), by ≤ 20 GETs/min against an endpoint the watchdog already polls
4×/min, and structurally by `ThrottledOrderExecution`; `guard_timeout_s` is REUSED
but the attempt COUNT is a separate constant from entry's (`loop._GUARD_ATTEMPTS`
vs `entry._GUARD_ATTEMPTS`, deliberately not shared — the two bursts have
different consequences when spent, and an exit must never retire anything); scope
drawn by POSITION, not exception type, with `AuditWriteError` re-raised untouched
ahead of everything (a dead recorder must halt). **`walk.started` moved BELOW the
guard** — a question asked before anything is sent did not start a walk, and the
2026-09-03 trail carried the proof (`walk.started: 11` against
`walk.finished: 10`) — **and above the `blocked` return**, so `BLOCKED` keeps its
pair. **Known consequence, accepted**: a burst that succeeds on attempt 2 or 3
submits at a limit priced 1–3s earlier, and the exit walk has no drift check on
its first rung — which is why the ladder is the fast one (1s, 2s); the walk itself
is the correction. **What this cost**, measured against the day's own control: the
session ran two adjacent call spreads entered five minutes apart, both triggering
`credit_multiple` in the same window — one watchdog survived, one did not. The
sibling realized 1.70; the blocked exit was worth about −190 against a
held-to-settlement −860, so **the halt cost ≈ $670 on one 2-lot spread**, and
`tools.mark` scores the pair independently at *"exiting early saved 660.00"* —
every dollar of it from the position whose watchdog lived. **Manual recovery**:
Richard restarted at 15:37:49 ET; the watchdog was running by 15:37:57 — eight
seconds — and within two ticks had adopted the spread, fired, walked and closed it
at 5.00 (fair value, deep ITM by then), flat two minutes before settlement.
Kill-switch persistence worked exactly as specified (came back `engaged`,
`restored: true`, original 15:04:05 press time, `halted: false` beside it).
**Still owed**: `HaltGrade` for a watchdog exception is still `ALL` and
`_halt_on_exception` still sets the shared stop event — this removes the cause
that fired, not the question P3 answers one source further along.
→ [the exit's duplicate guard, unreachable](../decisions/2026-09-03-exit-guard-unreachable.md)

**A submit the venue refused outright was reported as an absence — `no_order_exists`,
`reject_reason: null` — while the exception naming the exact unsupported symbol sat
in scope and was discarded.** The 2026-09-02 pass filed this as *"not urgent…
only the explanation is wrong."* 2026-09-03 made it the day's **dominant failure
mode**: 5 of 7 entry attempts (71%) died as `no_order_exists` with no reason, and
`tools.desk`'s execution table was five identical rows with nothing to separate a
permanent `instrument_validation_failed: Trading of SPXW <symbol> is not supported`
(cert refusing a strike that exists in production's chain, since
`[marketdata] source = "live"`) from a transient `timeout_error` or a 502. It also
stopped being cosmetic: on the exit path `NOTHING_AT_BROKER` is retryable under
`_EXIT_SEND_ATTEMPTS`, so an unreported permanent refusal now *spends budget* —
three sends against a strike the venue will never accept, and the exit path burned
one that day. **The bug, in one sentence**: `_recover(state, what, exc)` has the
causing exception in scope for its entire body and threw it away at the one branch
that needed it — `by_identifier` can report the ABSENCE of an order; only `exc`
can say why there is one. **Fixed**: `WalkResult.mutation_error: str | None`,
populated from `_broker_text(exc)` (`f"{type(exc).__name__}: {exc}"`, bounded at
`models.MAX_REJECT_REASON_CHARS` — made public rather than duplicated so the two
bounds cannot drift), reaching `walk.finished`, `entry.finished`, `ExitReport`,
`desk`, and the four per-position alert surfaces. **Six decisions**: a dedicated
field, not folded into `reason` (an alert sweep exists to govern it, so it joins
the governed set rather than becoming a fifth ungoverned string); **two fields and
two keys, never one doing double duty** — `reject_reason` is what the broker said
about an order it ACCEPTED and then rejected, `mutation_error` is what it said
about one it would not accept at all, and `reject_reason: "timeout_error"` would
read as the opposite of what happened; *"present only on `NO_ORDER_EXISTS`"* is a
GATE in `_finish`, sibling to `reject_reason`'s and separate from it, unit-tested
directly because it has no production caller that could violate it (*a contract
nothing exercises is a comment* — it survived a mutation until a test drove
`_finish` itself); named `mutation_error` in the module's own vocabulary
(*"Reads are retried freely; mutations never"*) rather than the task prompt's
passing `submit_error`, because `_recover` is shared and a failed REPRICE lands
there too; **renamed before the first deploy on purpose** — an audit payload key
is free to change until a row carries it, and after a deploy it would have cost
the log two names for one concept forever; and **nothing decides on it** — an AST
test refuses any comparison with `mutation_error` as an operand and any string
matcher on it across `loop.py`, `watchdog.py` and `entry.py`, because
permanent-vs-transient from broker prose is the tempting wrong fix and remains a
separate decision. `tools.desk` prints the reason BELOW its execution table (not
as a column — broker prose is long and the operative question is *which of these
are the same cause*), reading `p.get("mutation_error")` so a day spanning the
deploy still renders. **Found on the way**: the 2026-09-02 alert sweep was not
enforcing its own first field — `carries_payload` counted ANY `**`, and
`_record_exit` unpacks `**spread.credit_payload()`, so deleting `reject_reason`
from that hand-built alert left the suite green. Tightened to require the `**` be a
`to_payload()` call; a residual looseness (the hatch accepts any `to_payload()`,
not a `WalkResult`'s specifically) is AUDITED — all five governed sites
enumerated, nothing relies on it — and not filed as work. **Not done**: `/status`'s
spent-exit row still carries neither field (pre-existing, governed by `_SEAMS`
when it is done); any permanent-vs-transient distinction (explicitly a non-goal);
the `NO_ORDER_EXISTS` retry classification and the entry/exit asymmetry
(unchanged).
→ [a submit refusal is not an absence](../decisions/2026-09-04-a-refusal-is-not-an-absence.md)

## Deploy

Rebuild only. No config change, no migration to stage, no new audit category — the
image is the entire deploy.

```bash
cd /opt/argus
git checkout v0.3.16
git status --short                          # must be clean (or the expected argus.toml edit)

sudo docker compose build --build-arg ARGUS_VERSION=$(git describe --tags --always --dirty)
sudo docker tag argus:local argus:v0.3.16
sudo docker images argus                    # confirm the version tag is there

sudo systemctl restart argus.service

# Confirm what is actually running — either read alone is enough.
sudo journalctl -u argus.service -n 50 | grep 'argus build'
curl -fsS -H "Authorization: Bearer $ARGUS_KILL_TOKEN" \
     http://<tailscale-ip>:8443/status | grep -o '"version":"[^"]*"'
```

The `--build-arg ARGUS_VERSION=...` rule from v0.3.15 stands unchanged: omitting it
builds fine and reports `"unknown"`, and a bare `systemctl restart` with no fresh
build silently reattaches to whichever image was last built. Build, tag, restart,
then read the version back.

**Rollback is `git checkout v0.3.15`, image-only** — no config to revert, no
migration to reverse. A prior image simply never reads `Order.mutation_error` or
`WalkResult.mutation_error`, never emits `order.direction_disagreement` /
`watchdog.note_fills_disagreement`, and falls back to `infer_direction` for every
order's direction (the pre-fix behaviour, wrong only on a relabelled chained
close, which is benign on a full close).

**After deploy, what to look for:**

- `/status`'s "Build" row and the startup log's `argus build:` line showing
  `v0.3.16` (or `v0.3.16-dirty` if `argus.toml`'s droplet-local edit is present).
- On any chained-book session, `orders.direction` on a closing order reading
  `close` — and a `order.direction_disagreement` Tier 2 record written from
  `submit`/`replace` (not from the polling path) when the broker's echoed legs
  disagree. It never halts and never pages.
- A `note_fills` on a relabelled opening fill no longer suppressing
  `held_but_unbooked` — the page fires as it always should have, and
  `watchdog.note_fills_disagreement` records the mismatch.
- Any entry or exit `no_order_exists` now carrying a `mutation_error` string
  (`instrument_validation_failed: ...` or `timeout_error: ...`) rather than
  `null`, and `tools.desk` printing a "submit refusals" section below the
  execution table on a day with any.
- An exit-side `NOTHING_AT_BROKER` that is really a permanent instrument refusal
  still spends its 3 sends — this release explains it, it does not stop it. The
  `NO_ORDER_EXISTS` retry classification is unchanged and explicitly still owed.
- No new halt behaviour from the exit guard: a cert outage during an open
  position's exit should now produce `NOT_ATTEMPTED` and a re-ask on the next
  tick, with the watchdog, the mark and the 15:30 flatten all intact — the
  opposite of 2026-09-03.

## Scope

**Closes three items from the 2026-09-01/2026-09-02 live-fire passes and
v0.3.15's own first live-fire day:**

- The standing open decision "where should an order's DIRECTION come from" —
  answered *the identifier, wherever one exists*, signed off 2026-09-03 (mint over
  infer, `note_fills` in the same pass, no backfill).
- The exit-guard-unreachable halt from 2026-09-03 — the third and last instance
  of the "unreachable is an exception, not a verdict" class, the other two closed
  2026-08-26.
- Finding 6's follow-up from the third live-fire day, and the
  `argus_submit_failure_broker_reason` task prompt — a submit refusal reporting as
  an absence.

**All three were designed against the same principle**: where Argus's own record
(a minted identifier, a typed exception, an exception still in scope) disagrees
with a value inferred, defaulted, or nulled downstream, the record is the answer.

**Deliberately NOT in this release**, carried forward:

- **`HaltGrade` for a watchdog exception is still `ALL`** and still sets the
  shared stop event. This release removes the 2026-09-03 cause; it does not
  answer whether a genuine watchdog defect should keep taking the flatten down
  with it. P3's question, one source further along; the 2026-09-01 `EntriesEnded`
  split is its precedent.
- **Any permanent-vs-transient distinction on a submit refusal.** `mutation_error`
  reports the broker's words; nothing branches on them. Building that by matching
  the text is the tempting wrong fix and is a separate decision — the same one
  `entry.py`'s standing reject-reason prohibition already names.
- **The `NO_ORDER_EXISTS` retry classification**, on either path, and the
  deliberate entry/exit asymmetry (entry does not retry it; the exit does, under
  a 3-send budget). Unchanged.
- **No backfill of the three durable `orders.direction = 'open'` rows** from
  2026-09-01 — Richard's explicit decision. They stay as the historical record of
  the bug; the correct value is durable at Tier 1 if ever wanted.
- **`/status`'s spent-exit row carries neither `reject_reason` nor
  `mutation_error`.** Pre-existing, out of scope here, governed by the `_SEAMS`
  completeness test when it is done.
- **`execution.walk_source` / `watchdog.trigger_source`** still carry
  SANDBOX-ENTRY values; the owed data-backed pass is unchanged by this release.
- **The PARTIAL-close-on-a-chained-pair precondition** is still unexercised — the
  direction fix makes it safe when it fires, it does not make it fire.

**The daily max-loss circuit breaker remains structurally inert in sandbox**,
unchanged by this release. Proving that rail out is still a live-flip gate.

**Test suite: 1955 passing, up from 1927 at v0.3.15** — 28 new tests across the
three fixes. Per-fix, from the decision records: the direction fix adds behavioural
coverage in `tests/test_execution_models.py` (the real 2026-09-01 orders — 618918
still maps OPEN, 619079 and 625205/625224 now map CLOSE), `tests/test_order_audited.py`
(the two Tier 2 telemetry categories, mutation-verified against a `raise` and a
Tier 1 reroute), `tests/test_working_orders.py` and `tests/test_order_store.py`,
plus an AST test pinning parse-before-inference in `map_placed_order` and the
first-write-wins `direction` column. The exit-guard fix adds six behavioural tests
(`tests/test_watchdog_exit.py`, G1–G6), the `walk.started` pairing assertion in
`tests/test_execution_loop.py`, and an extended T5 AST sweep; the test that pinned
the old halting posture is **replaced, not deleted**, its one load-bearing
assertion (`broker.submitted == []`) surviving verbatim — seven mutations run, all
seven caught. The submit-refusal fix adds six (`tests/test_execution_loop.py`
S1–S4, `tests/test_desk.py` S5–S6, the second covering a pre-deploy row that lacks
the key), the sweep tightening, and an updated closed key-set assertion in
`tests/test_entry.py` — nine mutations run, all nine caught, one of them surviving
until a test drove `_finish` directly.
