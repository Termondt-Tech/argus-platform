# v0.3.2

Fixes the reconciliation halt that cost the 2026-08-14 session. Requires an image
rebuild — this is a `src/` release. **No config change**: `argus.toml` and
`blackout_dates.txt` are unchanged from v0.3.1.

## Fixed

**The sandbox 24h reset cleared the order ledger and hard-halted the next
trading day.** On 2026-08-14 startup reconciliation refused the day with three
`unexpected_filled_order` discrepancies and crash-looped 34 times, paging Slack
on every restart. All three orders were Argus's own, from the previous
live-fire session.

Two windows were being treated as one. The reset stand-down keys on a
trading-DAY rollover in ET; `get_live_orders()` reaches back a rolling 24
HOURS. Thursday's fills at 14:00 and 14:22 UTC were still inside that lookback
when Friday reconciled at 13:40 UTC — 23h18m to 23h40m later. The reset ran
first, deleted the ledger rows for exactly those orders, and `known_orders()`
then had nothing to match the broker's report against.

Cert also turns out to wipe **positions but not the order record**, contrary to
the vendor documentation the rail was built from. The reset now clears
`positions` only (`clear_reset_positions`); `orders` and `order_legs` survive.

Retention can only remove false halts — the check flags broker orders absent
from the ledger, so a genuinely foreign order still halts, and the
duplicate-submission guard is unaffected because it asks the broker, not the
ledger. A retained order rebuilds no phantom spread for the watchdog:
`_pair_spreads` already gates on a non-zero `positions` row. Live is untouched;
the clear has always been sandbox-only.

One coverage gap is created and recorded rather than papered over: an order of
Argus's own left WORKING overnight is now "known" and passes the order
reconcile. Cert has never done this, and the fix if it is ever needed is a
past-trading-date check on working orders — not a return to wiping the ledger.
