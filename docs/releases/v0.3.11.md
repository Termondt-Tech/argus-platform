# v0.3.11 — Sadachbia

*TAGGED. (This heading read "DRAFT. Not yet tagged." until 2026-09-10.) Named per the Argus's Eyes convention
(`docs/releases/README.md`) — γ Aquarii, Arabic *Sa'd al-Ahbiyah*, "the Eye /
Watcher of Hidden Things." Spent from the pool, and it fits precisely rather than
approximately: every part of this release is a condition that had **no instrument
watching for it at all**, not a known state read wrong. A broker call that could
not be answered fell to the same generic handler a genuine bug does — there was no
rail for "could not ask" distinct from "asked and disagreed," so it either killed
the process or was misfiled as `session.error`. The entry path had the same hole
one call over, where it cost trading days instead of processes. And a timeout
contract silently broken by an httpx scalar default sat invisible for the whole of
v0.3.10, because the one test written against it watched a single phase and never
the other three. All of them were found the same way — reading raw production logs
directly, because the audit trail itself had nothing to say.*

**Requires an image rebuild AND a config update, and they must deploy together.**
`app.py`, `session.py`, `reconcile.py`, `config.py`, `status.py`,
`account/refresher.py` and `execution/entry.py` all change.
`argus.toml`/`argus.dev.toml` gain a new **required** `[reconcile]` section and
two new **required** `[execution]` keys — an old config against the new image
refuses to start (`missing or malformed [reconcile] section`, or `missing required
config key execution.guard_timeout_s`), and the new config's keys mean nothing to
the old image. Same coupling `watchdog.exit_unattempted_max_s` already needed
(v0.3.7).

## Fixed

**A broker that could not be ASKED fell through the same path as a genuine
bug, and killed the process.** 2026-08-26: `v0.3.10` restarted intraday on a
confirmed blackout day, hit a cert 502 on the process-start reconcile, and — because
`TastytradeError` is not `ReconciliationError` — fell to `startup()`'s generic
`except BaseException: teardown; raise`. The process exited; Docker restarted it;
cert 502'd again. **Five `process.start` records in 33 seconds**, no
`process.stop` between any of them, no `reconcile.result`, and no `/status` or
`/kill` reachable for the whole episode — a `reconciliation_mismatch` halt gives
all three; this gave none. The same evening, a `ReadTimeout` on the per-day
reconcile propagated past `run_session`'s own handler to `app.py`'s catch-all and
was recorded as `session.error`, under a comment claiming *"reaching here means a
genuine bug."* A network timeout against an API this codebase's own comments
document as hanging and 502-ing is not a bug.

**The invariant — a mismatch must never be retried past — is now held by
mechanism, not discipline.** `Reconciler.reconcile()` has always *returned*
`ReconciliationResult(ok=False)` on a disagreement rather than raising; it never
travels as an exception. So a bounded retry that wraps only the broker AWAIT
(never the comparison) is structurally incapable of retrying past a mismatch — a
mismatch exits the loop on the first pass having spent zero attempts. Bug-vs-fetch
is scoped by POSITION in the call graph rather than exception type, because a type
list would have missed the raw `httpcore2.ReadTimeout` that actually escaped in
the incident. One type is a deliberate exclusion: `AuditWriteError`, which can
surface from inside `get_live_orders()`'s own Tier 1 write and must never be
retried (no auto-retry on a dead recorder, CLAUDE.md).

**"Could not ask" now retries — 3 attempts per broker call, `min(2·n, 5)`
backoff, reusing `_fetch_accounts`'s cadence — inside an outer loop that retries
the whole reconcile every 60s for up to 30 minutes.** The outer loop never enters
the halted state while it is still trying: the control surface already binds
before the reconcile (2026-08-17), so a process mid-retry is alive, bound, serving
`/status` and `/kill`, not trading, and not halted — a success needs nothing
undone. Only exhaustion is terminal:

- **Process start PARKS** — the same `_halt_process` seam a mismatch has used
  since 2026-08-17, `source="broker_unreachable"`. This overturns the CONSEQUENCE
  of the comment at `app.py:952` (*"tears the half-built process down"*), which
  was true when written and stopped being true the moment the control bind moved
  ahead of the reconcile — the comment's PREMISE (*"could not ask is not nothing
  to report"*) is unchanged and, under the park, is honored more completely than
  before: a Tier 1 record, an alert, and `/status` reading HALTED with the reason,
  where the old exit gave none of the three.
- **Per trading day ABORTS THE DAY, and does not halt the process** — a mismatch
  means Argus's model is known-wrong (permanent); unreachable means unknown
  (tomorrow re-asks). Neither response starts a watchdog, so the only real
  difference is whether the operator is told — which is why the alert moved into
  the shared retry function rather than staying on either call site's own
  terminal handler: `session.aborted` fires no Slack alert of its own, so leaving
  it there would have made the fix quieter than the `session.error` it replaces.

A wrong `account_number` in config stays `SessionAborted` and parks immediately,
never retried — an outer loop spending 30 minutes re-proving a permanent
misconfiguration would be its own defect. The login leg (`tt.open()`) gets the
park but explicitly **no retry**: each failed OAuth refresh accrues toward
tastytrade's undocumented IP-block threshold, and `_login_with_retry` already
spaces its own attempts a flat 10 minutes apart for that reason — retrying login
on the reconcile's 60s cadence would be 5x more aggressive than a number chosen
against a ban risk.
→ [broker unreachable](../decisions/2026-08-26-reconcile-broker-unreachable.md),
[design](../designs/2026-08-26-reconcile-broker-unreachable.md)

**One unanswered duplicate-order check ended the whole trading day, and it had
already done so twice.** The same shape as the reconcile hole above, one call over
and on the entry path: `DuplicateOrderGuard.has_conflicting_order` raises when it
cannot reach the broker — correctly; an unanswerable question must never read as
permission — and in live-fire that raise called `_end_day` on the **first**
failure, with no retry at any level. 2026-08-25, **10:00:00 ET, the day's very
first tick**: a gate-approved 5-wide 7700/7705 at 0.525, one timed-out
`get_live_orders()` against a cert already showing 25 `account.refresh_failed`
that morning, and ~5 hours of entry window gone. No order was ever at risk.

**Two things the investigation turned up that were not part of the complaint.**
The guard call had **no bound of its own**: it inherited `broker.http_timeout_s`
(30s), which that key's own config comment sizes for *"a cold FIRST authenticated
call from a new host"* — and httpx reads a scalar as connect/read/write/pool
independently, the same trap fixed below in `account/refresher.py`, so the real
worst case was ~60s of blocked signal loop *before* the day ended. A retry without
its own per-attempt bound would have tripled that, which is why
`execution.guard_timeout_s` is part of this change and not a follow-up. And
**`_end_day` costs more than the entry window**: it unwinds `run_session`'s
`finally`, which stops the *watchdog*, so a spread already open when it fires stops
having its virtual stop evaluated — on expiry day — and the scheduler never
re-enters a day it has already run. That argues for reaching `_end_day` rarely,
never for softening what happens once it is reached.

**Fixed in two stages, neither of which touches what counts as a conflict.** A
bounded burst — 3 attempts, 1s/2s backoff, each under `execution.guard_timeout_s`
(3.0) — absorbs the single blip at zero cost, not even a retired candidate. A
spent burst retires that trade idea and pages, exactly as the dry-run path has
since 2026-08-11. The day ends only on `execution.guard_unreachable_max_streak`
(3) spent bursts **back to back**, and takes the original posture completely
unchanged: `_end_day`, no kill switch, the same `entry.aborted_day` record with
the same `kind` and the same raw `error_type`, plus two additive fields.

**The streak counts DISTINCT TRADE IDEAS, not ticks.** `_attempted` claims the
candidate *before* the guard runs and `candidate_id` keys on the strike pair, so
the next 5s tick re-proposing the same strikes returns at
`entry.already_attempted` and never reaches the guard — which also means the
obvious "let the next tick try a fresh one" design was never actually available.
Releasing that claim was considered and **refused**: it would turn an
unconditional *"claimed before anything can reach the broker"* into a conditional
one, in the single arc that prevents a double entry.

**The duplicate invariant survives by the mechanism it always had**, not by new
discipline: `_walk_and_report` is unreachable without a returned `ConflictVerdict`,
`guard.py` is untouched (WORKING/FILLED block, DEAD allows, unclassifiable
blocks), and a blocked verdict returns on the first attempt having spent no
retries — the retry is on the QUESTION, never the verdict, the same structural
property the reconcile fix rests on. Four independent mutations each fail at least
one test. `entry_build_failed`, the only other `_end_day` site, is deliberately
untouched: nothing in its `try` touches the network, so a retry there would spin
on a permanent defect.
→ [entry guard unreachable](../decisions/2026-08-26-entry-guard-unreachable-retry.md)

**`session.error` recorded nothing about what failed.** Diagnosing the incident
above needed a live `journalctl` dig specifically because the payload carried only
`{"trading_date": ...}`. Now carries `error_type` and a 500-char-truncated
`error`, matching `account.refresh_failed`'s shape, on both the audit record and
the Slack alert. No behavior change — purely what gets written down about an
exception that already propagates exactly as it did before.

**The account liveness refresher's own timeout contract was silently broken —
found the same evening, from the same production reading.** `refresh_now`'s
backstop (`refresh_interval_s`, documented as *"if it ever fires the bug is in the
port"*) fired 5 times on 2026-08-26. Cause: `_leg` passed a SCALAR `timeout=` to
httpx, which sets connect/read/write/pool to that value **independently** — so a
single leg could spend the whole budget connecting and the whole budget again
reading, and a nominal 5s attempt could reach ~20s. Between the two legs the
deadline was real (v0.3.10's whole point); within one request it never was, and
the module's own docstring claim of "one monotonic deadline" was true for one
scope and false for the other. **The pre-existing test asserted only the READ
phase**, which is exactly why this sat invisible for the whole of v0.3.10.

Fixed by bounding the phases that were never the point: READ keeps the full
remaining budget (it is the phase the budget exists for), and connect/write/pool
get small FIXED ceilings (1.0s / 0.25s / 0.25s) that do not scale with the budget.
Worst case per leg is now `remaining + 1.5s`, not `4x remaining`. Sized from the
same outage that exposed it — across ~1,464 refresh failures that day there was
not one `ConnectTimeout`; every one was a read timeout or a fast 502, so a tight
connect ceiling costs nothing. Three new tests pin the three phases the old suite
never looked at; reverting the fix fails two of them.
→ [account refresh off the event loop](../decisions/2026-08-26-account-refresh-off-the-event-loop.md)

## Changed

**v0.3.10's "DEPLOYED, NOT PROVEN" is now PROVEN**, by an A/B nobody planned. The
deploy landed intraday, so the same trading day held both code versions under
identical, and identically bad, broker conditions — cert's internal authorization
service (`/customers/me/permitted`) was 502-ing through their consul mesh for six
straight hours, with the nginx version flapping between `1.31.0` and `1.31.3` on
consecutive responses (an unhealthy pool member behind their load balancer, not an
Argus-side cause). Splitting the journal by PID:

| | code | window | refresh fail/min | breach episodes | breaches/min |
|---|---|---|---|---|---|
| old (on-loop `gather`) | 127.2 min | 3.99 | **140** | **1.47** |
| new (threaded) | 237.2 min | 4.04 | **1** | **0.013** |

Failure volume held flat — the control, and the half that must NOT improve, since
the pool still empties and every refresh is still cold. Event-loop breaches fell
**~115x per minute**. The single new-code episode fired before that process's
first refresh failure (the documented chain-subscription startup stall); across
four hours under sustained failure the loop breached zero times from account
refreshes. Method and the full reading are recorded in the decision, including
**always split by PID when a day spans a deploy** — a whole-day aggregate
silently mixes code versions, which is how the first pass at this same data
produced three "failure categories" that turned out to be two code versions
wearing different error messages.

## Deploy

Rebuild AND config move together.

```bash
cd /opt/argus
scripts/argus-deploy.sh --dry-run v0.3.11   # show the plan, touch nothing
scripts/argus-deploy.sh v0.3.11             # deploy it
```

`argus.toml` gains the `[reconcile]` section (three required keys —
`request_timeout_s`, `retry_interval_s`, `retry_budget_s`) **and two required
`[execution]` keys** (`guard_timeout_s`, `guard_unreachable_max_streak`); `git
checkout v0.3.11` brings all five in the same commit as the code that needs them,
so a normal deploy already carries both halves together. Confirm with `git status
--short` after checkout that `argus.toml` actually moved.

**Rollback needs BOTH halves, unlike v0.3.10's rebuild-only rollback.**
`git checkout v0.3.9` (or whichever prior tag) alone reverts the config too, so a
plain image-tag rollback (`ARGUS_IMAGE_TAG=<previous>` without the checkout) would
leave the new `[reconcile]` section and `[execution]` keys in place against code
that never reads them — harmless (unused keys), but confirm the checkout ran rather
than assuming one half is sufficient the way it was last release.

## Scope

**Closes the process-start restart storm and the per-day misfiling from
2026-08-26**, plus the residual the same production reading exposed in the
refresher's timeout contract. All three from one evening's incident.

**Also closes the entry guard's identical shape** — the same "could not ask" hole
one call over, where it cost trading days rather than processes
([prompt](../tasks/argus_entry_guard_unreachable_retry_prompt.md)). Fixed
LOCALLY, not by unifying it with the reconcile: the placement that would have
unified them — retrying inside the execution adapter — is **forbidden**, because
`Reconciler.reconcile()` and the entry guard call the SAME port method
(`get_live_orders()`), and a retry there would push a ~72s budget into an await on
the entry pipeline's 5s signal cadence. Three locally-reasoned fixes, one shared
vocabulary: the entry path's own `_GuardUnreachable` is private and never escapes
its module, but carries `BrokerUnreachable`'s payload field names so all three
sites read alike in the log.

**Also closes out v0.3.10's own open item** — the production before/after is
taken and recorded (see Changed, above).

**Two things explicitly NOT done, each for a reason stated in its decision
record:**
- **N consecutive unreachable *days* escalating to a halt** at the per-day
  reconcile site — the 30-minute intraday loop makes one bad day survivable, not
  five in a row, and there is no evidence yet for what N should be. The entry
  guard's streak has the same open end, one level down.
- **The dry-run branch's own 30s inherited bound.** `execution.guard_timeout_s`
  applies to live-fire only, deliberately: that mode routes nothing, so there is
  nothing for patience to protect, and its soft-abandon has been correct since
  2026-08-11. A pre-existing condition of a transitional activation mode, not
  something to fix on the way past.

**Not included, and needs a decision before it rides any release:** the three
residuals from the 2026-08-20/21 proactive review
(`docs/tasks/argus_b2_e1_c1_stability_residuals_prompt.md`) — none touches the
same call paths as this release's work, so there is no technical reason they move
together, and two of the three are design-gated and unstarted.

**The daily max-loss circuit breaker remains structurally inert in sandbox**,
unchanged by this release. Proving that rail out is still a live-flip gate.
