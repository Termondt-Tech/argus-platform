# v0.3.20 — Zubeneschamali

*The deploy plan learns the third release shape, and stops restarting the trading
process for changes it cannot read. v0.3.19's own deploy is the worked example: a
release whose entire content was the deploy script reported **"skipping build
(config-only release)"** — the wrong class, on the one release where the class was
the whole point — and then bounced the session anyway. A restart is not free: it
tears down the session, the watchdog, the virtual stops and the marks, and it is
the one deploy step carrying a timing rule. The question the plan now answers is
not "which class is this?" but **"is there anything here the running process can
see?"*

*Named per the Argus's Eyes convention (`docs/releases/README.md`). Neither pool
candidate fits (**Aldebaran** reserved for the live-min-size flip or a clean
re-watch; **Rastaban** for dual-watchdog / consensus), so the name comes from
outside the table, the pattern since v0.3.6. **Zubeneschamali** — β Librae, Arabic
*al-zubānā al-shamāliyya*, "the Northern Claw" — is a star **that is not where its
name says it is**: it is the Scorpion's claw, catalogued into Libra when the scales
were carved out of Scorpius, and every chart since has had to carry the correction.
That is this release exactly — a deploy that named `scripts/` a config release and
acted on the label rather than on the thing. It qualifies by **tradition, not "eye"
etymology** — Alcor's standing — and it is a fair fit twice over, since the fix is
to stop classifying by name and start asking what the process can actually reach.
**Aldebaran and Rastaban stay reserved.***

*Then the same release found what that classifier had been missing, one unit over.
v0.3.18 gave `docker-compose.yml` a `${ARGUS_ENV:?}` that refuses rather than
interpolating when unset — on `build` and `run`, not only `up`, because
interpolation happens when the file is parsed. `argus-snapshot.service` had no
`EnvironmentFile`, so **from that deploy the nightly backup died inside `docker
compose run`, before SQLite, every night** — and it was invisible from every
downstream surface: the NAS kept connecting on schedule, `rsync --ignore-existing`
kept finding nothing new, and `pull.log` kept writing `pull complete` over a backup
set that had stopped growing. With Litestream deferred past go-live (2026-09-04),
that snapshot is the **only** off-box copy of the hash-chained audit log.*

**`scripts/` + three systemd units + tests + docs. No `src/`, no config, no image**
— and it is the first release the new logic classifies for itself: `build: no`,
`config: no`, `restart: no`, and no `unit:` line at all (that one prints only when
`argus.service` moves). The checkout is the deploy. **Three unit files still need a
manual `sudo cp`** — see Deploy.

## Fixed

**The plan names all three shapes, and the restart is decided by what the process
can reach.** A release is now classified by asking, of every changed path, whether
the running container can see it — and it is answered **fail-closed, by
elimination**. Each path must be *affirmatively* recognized as inert or the restart
happens; a file class nobody thought of restarts, which costs a session rather than
a rail.

Inert, with the reason attached to each: `scripts/` (which *is* the deploy rather
than an input to it — and by the time it could matter, v0.3.19's hand-over has
already run it), `docs/`, `tests/`, `README.md`, `CLAUDE.md`, `.gitignore`,
`fomc_dates.txt` and `discretionary_blackout_dates.txt` (generator inputs — the
process reads only the product), and **another profile's config**. That last one is
routine now that the profile split exists: a live-config edit landing on the cert
droplet is a real config change and a complete no-op here, and reporting it as
`config: YES` reads as riskier than it is.

The rule underneath, stated once so it can be checked: **the container can see the
image, the two bind mounts (this host's `argus.<profile>.toml` and
`blackout_dates.txt`) and the systemd unit — nothing else in this repo.** The plan
now prints:

```
  config: not for this host — argus.live.toml moved, but profile 'sandbox' does not mount it
  build: no (src/requirements.txt/pyproject.toml/Dockerfile unchanged since v0.3.19)
  restart: no — nothing the running process can see moved.
         inert: docs/x.md scripts/helper.sh
         (a restart tears down the session, the watchdog, the virtual
          stops and the marks. Pass --restart to force one.)
```

**`--restart` forces one anyway**, and two cases restart unconditionally without
it: a build (`--force-build` with no changed inputs still produces an image only a
restart picks up) and a unit sync. **Re-deploying the tag already checked out also
restarts** — that is the documented crash-container recovery path and it must keep
working.

**The read-backs follow the restart rather than assuming one.** With no restart
there is no boot to anchor `--since` to, so the version and config queries switch
to "the last startup line, whenever it was" (via `journalctl --grep`, so a
long-running process's log volume cannot push it out of a window), and the question
they answer weakens honestly: not *did the new process come up right?* but **is
what has been running all along still what this tag expects?** That is worth
asking — it is how a droplet hand-edited since its last restart, or a config
release that was checked out and never restarted, gets caught. When the sha
mismatches on a no-restart release the message says so explicitly: *the mismatch
predates this deploy.* The red-flag journal grep is skipped entirely in that case,
because the recent lines describe a process this deploy did not touch and judging
them would report an unrelated pre-existing condition as this release's failure.

**The nightly snapshot has been failing since v0.3.18, and nothing said so.**
`scripts/argus-snapshot.sh` reaches the DB through `docker compose run`, which
since v0.3.18 refuses without `ARGUS_ENV`; `argus-snapshot.service` supplied none.
Fixed on **both** paths, because either alone leaves a hole: the unit now carries
`EnvironmentFile=/etc/argus/host.env` with **no `-` prefix**, exactly as
`argus.service` does, so a missing profile fails the *unit* rather than starting it
profile-less and dying one layer down; and the script refuses loudly, naming the
command to use, for the hand-run path where systemd is not involved and `sudo`
scrubs the environment.

Two properties of the failure worth carrying. **Nothing was destroyed** —
rotation is the last step of the script, downstream of the backup and under
`set -e`, so a job that dies at interpolation never rotates; the retained snapshots
are frozen exactly as they were, and the loss is new coverage only. And **the
calendar was generous**: the first failed run was Saturday 2026-09-05, with
2026-09-06 a Sunday and 2026-09-07 Labor Day (`argus.sandbox.toml:761`), so the
last good snapshot — Friday 09-04, 16:30 ET — already contains everything through
Friday's close. The first run that would have cost real coverage is **Tuesday
2026-09-08**.

**Every documented `docker compose` command was stranded by the same change**, in
`README.md` and the deployment runbook. They still looked right and could not run.
Two rules now hold across both, stated once each and then applied literally rather
than described:

- **The profile is read, never typed** — `PROFILE="$(sudo sed -n
  's/^ARGUS_ENV=//p' /etc/argus/host.env)"` once per shell, with a
  `test -f argus.$PROFILE.toml` beside it. `host.env` is per host, is not in git,
  and is the one file the live cutover changes, so a hardcoded `sandbox` is a
  command that works today and is wrong the morning after the flip. The same now
  applies to `--config`, which had the identical defect one argument over: only
  *this* host's config is bind-mounted, so a literal `argus.sandbox.toml` on a live
  box names a file that is not merely stale but **absent**.
- **`sudo` scrubs the environment**, so a `sudo` line carries
  `ARGUS_ENV="$PROFILE"` inline, always. An `export` earlier in the block does not
  reach it, and `PROFILE=` supplies the *value* for an inline assignment — it never
  substitutes for one. Only a local, non-sudo line may lean on a block-local
  `export`, and those now say so.

The `test -f` earns its line: it catches an unprovisioned `host.env`, a typo, a
profile whose config the tag does not carry, and a `host.env` written with
**quotes** — systemd accepts `ARGUS_ENV="live"`, the one-liner hands back `"live"`
with the quotes attached, and compose then looks for `argus."live".toml`. Runbook
§8.0 states the no-quotes requirement where the file is created.

The README's tools block previously dropped the prefix *"for width"* and told the
reader to add it back. That is the wrong trade for a block whose only purpose is
copy-paste: **the line you copy is the line that has to run.**

## Added

**A droplet-side check that the NAS backup pull is alive** —
`scripts/argus-pull-check.sh` + `argus-pull-check.{service,timer}`, daily at 09:00
ET. It lives on the droplet and not on the NAS deliberately: on 2026-08-09 a power
outage rebooted that device, its crontab went with it, and **nobody noticed for
seventeen days**, by which point the droplet's 14-snapshot retention had rotated
two days of files off the back that the NAS had never received. Every mechanism
*on* the NAS shares the fate of the device it runs on; a watcher has to live
somewhere that survives independently.

**It checks both sides, independently, and both must hold.** A check that asks only
*"did the NAS log in?"* reports green through a total snapshot outage — which is
precisely the state above, and is why the two are separate assertions rather than
one:

| Side | Question | Default | Override |
|---|---|---|---|
| Producer | Is the newest `/path/to/backups/argus-*.db` recent? | 26h | `ARGUS_SNAPSHOT_MAX_AGE_H` |
| Consumer | Has the `nas_pull_key` fingerprint authenticated? | 48h | `ARGUS_NAS_MAX_AGE_H` |

26h is one nightly cycle plus slack — a single late run does not page, a skipped
night does. The two fail for unrelated reasons and **neither is visible from the
other's vantage point**. Had it been running, the producer arm would have paged on
the morning of 2026-09-06, ~40h after the last good snapshot.

It checks the **symptom**, never a particular cause, so a wiped crontab, a dead
daemon, a stale pidfile, a rotated host key, a changed droplet IP, a full NAS disk
and a broken `rrsync` restriction all surface identically. It **fails closed**: an
unreadable public key means NAS logins cannot be identified, and *"cannot tell"*
must never render as *"fine"* — the same rule the app applies to an unreadable
account snapshot. A silent NAS exits non-zero on purpose, so
`systemctl list-units --failed` is a second signal that does not depend on Slack
having been delivered — which matters here, because the failure the whole unit
exists to catch was itself a notification that never arrived.

**The NAS end is hardened too, and the diagnosis behind it replaces a folk
belief.** `/proc/cmdline` on that device says `root=/dev/ram`: `/` is a RAM disk
unpacked from the firmware image at **every** boot, so `/var/spool/cron/crontabs`
and `/root/.ssh/known_hosts` are discarded on reboot and only on reboot. That is
structural, not flaky firmware, and it retires the old advice to *"check
`crontab -l` in a day or two"* — a test that passes every time, because entries
survive arbitrarily long uptimes and vanish together at the next power event.
Three consequences, now fixed:

- `kill -0` is **not** a liveness test for *our* daemon — it asks only whether
  *some* process holds that pid. The pidfile is on the persistent partition and
  outlives a hard power cut while pids on that box are low and recycle fast, so
  afterwards that number very likely belongs to an unrelated WD process, `kill -0`
  succeeds, and the watchdog exits 0 forever having started nothing — silently
  disabling the only recovery mechanism there is. It now confirms the `cmdline`.
- `UserKnownHostsFile` moves to the data partition. Under the default
  `/root/.ssh/known_hosts` the host key was re-learned from scratch every boot, so
  `StrictHostKeyChecking=accept-new` re-trusted whatever answered. Trust-on-first-use
  is worth nothing if first use is every Monday.
- The `@reboot` crontab entry is **removed**. `/mnt` there is a 1 MB tmpfs that the
  data partition is mounted *onto* later in boot, so an `@reboot` job can fire
  before the script's own path exists and silently do nothing. The `*/15` entry
  covers reboot recovery anyway — by the time it fires, the disk is up.

**The classifier learns the ancillary host units.** `argus-snapshot.*`,
`argus-pull-check.*` and `argus-shadow.*` run on the host beside the container and
are unreachable from inside it, so a release moving only one must not tear down a
session. They are **named, never matched by a `*.service` glob** — `argus.service`
is the one unit in that class that must always restart, and a glob would swallow
it. But **inert is not deployed**: the deploy syncs `argus.service` and nothing
else, so the plan now prints an `ancillary units CHANGED` block naming each file
and the exact `sudo cp`. Left unsaid, a fix to a backup unit deploys green and
changes nothing — the silent-reattach failure one unit over, and with no read-back
available, because a timer reports no version.

`tests/test_deploy_wiring.py` gains the assertion that keeps the inert list honest:
**nothing `docker-compose.yml` bind-mounts may be treated as inert by the deploy.**
The two files have to agree and nothing else can notice if they stop — bind-mount a
new repo file without removing it from the classifier and a release changing that
file deploys with **no restart and no error**, the process still reading the old
contents while the deploy reports success. The test parses compose's bind sources
and the script's `case` arms, matching with `fnmatch` rather than equality (a glob
arm swallows a mounted file just as effectively as naming it) and comparing
*tokens* rather than substrings — `discretionary_blackout_dates.txt` contains
`blackout_dates.txt`, and a substring test would have passed on the one file that
matters most. Verified by mutation: making `blackout_dates.txt` inert fails it.

Rehearsed against a scratch repository across all five shapes — scripts+docs only,
another profile's config only, this host's config, `src/`, and an unrecognized new
top-level file (which correctly forces a restart) — plus `--restart` overriding the
first.

**Four more tests, and three of them exist because nothing else in this repo can
notice.** Neither operator doc is executable, so a stranded command stays green
forever; and a copy between a unit file and a script cannot fail loudly either.

- `test_every_compose_invocation_outside_the_deploy_carries_the_profile` — the
  v0.3.18 failure had a **second site**, and it was the one nobody watched.
  v0.3.19's test covered `argus-deploy.sh` only. This pins both halves of the
  snapshot fix, line-anchored: a commented-out `EnvironmentFile=` line contains the
  substring and supplies nothing, and the first draft of this assertion passed
  against exactly that.
- `test_ancillary_host_units_are_inert_but_never_silent` — the units are inert,
  `argus.service` is **not** in the inert set, and the plan names what the deploy
  will not install.
- `test_no_documented_compose_command_is_missing_the_profile` — walks every fenced
  block **and inline code span** in `README.md` and the runbook. The retained-logs
  table row is a command someone runs, and a check reading only fenced blocks says
  nothing about it. Inline spans are filtered to those carrying `sudo`, which
  separates a command to run from a prose reference to one.
- `test_the_operator_docs_never_hardcode_a_profile_into_a_droplet_command` —
  with one deliberate exemption: **writing** `host.env` is the single place a
  literal profile belongs, since that file is where the answer comes from and
  cannot be read from itself.

All mutation-checked. The first drafts of two of them passed against the regression
they existed to catch — one against a commented-out line, one treating a `PROFILE=`
preamble as excusing a bare `sudo docker compose` in the same block, which is
backwards, since `sudo` is what strips it. That is where the sudo-scope rule above
got stated precisely instead of loosely.

## Deploy

**No restart — and then three manual `sudo cp`s that the deploy deliberately will
not do for you.** Skip step 2 and this release is a no-op for the thing it exists
to fix.

### 1. The deploy itself

```bash
cd /opt/argus
scripts/argus-deploy.sh --dry-run v0.3.20
```

**The dry-run cannot show you this release's plan, and that is structural.** The
hand-over is gated on the checkout, and `--dry-run`'s whole contract is that
nothing is checked out — in v0.3.19's script the dry-run exits at line 291, the
checkout is at 313 and the hand-over at 342. So a release that ships a different
deploy script always dry-runs under the *old* one. Expect v0.3.19's wording:

```
  config: no (unchanged since v0.3.19)
  build: no (…unchanged since v0.3.19) — checkout + restart only
```

**`checkout + restart only` is v0.3.19 saying it would restart. It will not** —
v0.3.19 has no restart classifier, that is what v0.3.20 adds, and the hand-over
means v0.3.20's answer is the one that governs. This deploy is therefore a clean
demonstration of the mechanism: the old script plans a pointless session bounce,
hands over, and the new script declines it.

Read the dry-run for the two things it *is* authoritative about — `from: v0.3.19`,
and the config diff being empty. Then:

```bash
scripts/argus-deploy.sh v0.3.20
```

This is the first live exercise of v0.3.19's hand-over. Expect the plan **twice,
with different verdicts** — v0.3.19's first (`checkout + restart only`), then
`v0.3.20 ships a different deploy script (… -> …)` / `handing over to it`, then
v0.3.20's own plan carrying `restart: no` and the `ancillary units CHANGED` block.
**The second plan is the authoritative one.** `ARGUS_DEPLOY_PREV_TAG=v0.3.19` rides
across the `exec`; without it the re-exec'd copy would `git describe` itself as
v0.3.20, diff nothing against nothing, and conclude there was no work to do.

Do not read the absent restart as a failed deploy — the run ends with
`NOT restarting argus.service … THE CHECKOUT IS THE DEPLOY`, which is the
success case here.

`/status` will keep reporting `version: v0.3.18` and
`config: sandbox/argus.sandbox.toml @be5c42777173`, unchanged — correctly, since
neither the image nor the mounted config has moved since, and the deploy reports it
as `still running (not restarted)`.

### 2. Install the three unit files — REQUIRED

The deploy syncs `argus.service` and nothing else. The trading process cannot read
these, which is exactly why no restart happens; it is also why nothing downstream
will complain if you forget them.

```bash
cd /opt/argus && sudo cp argus-snapshot.service argus-pull-check.service argus-pull-check.timer /etc/systemd/system/ && sudo systemctl daemon-reload
```

`argus-pull-check.timer` is **new**, so `daemon-reload` alone will not start it —
it needs enabling. `argus-snapshot.timer` is already enabled and needs only its
unit re-read, which the `daemon-reload` above did:

```bash
sudo systemctl enable --now argus-pull-check.timer && sudo systemctl reset-failed argus-snapshot.service
```

### 3. Prove both, now — do not wait for 16:30

```bash
sudo systemctl start argus-snapshot.service && sudo systemctl status argus-snapshot.service --no-pager && ls -lt /path/to/backups/ | head -3
```

A fresh timestamped `.db` and `verified … (N records, chain intact)` in the journal
is the fix working. **Run it once.** `ARGUS_BACKUP_KEEP` counts files, not days, so
each extra run evicts another day off the back — and a snapshot is a full 490 MB
copy of the DB, not the "~7 MB" the script used to claim. `systemctl status` exits
**3** on a correctly-finished oneshot ("inactive (dead)" *is* success), so never
chain anything off it with `&&`. Then the check, which should report **both** sides on one line:

```bash
sudo /opt/argus/scripts/argus-pull-check.sh
```

Expect `argus-pull-check: ok — newest snapshot argus-<stamp>.db (0h), last NAS pull
<date>` — **both sides on one line**. A `:rotating_light:` here is real and worth
reading rather than re-running; it names which side failed, and distinguishes a
*blind* check from a *silent* NAS. **`sudo` is not optional**: the system journal
needs root and the producer arm does not, so an unprivileged run would otherwise
report *snapshot fresh, NAS dead.*

```bash
systemctl list-timers 'argus-*' --no-pager
```

Expect `argus-snapshot.timer` → next 16:30 ET and `argus-pull-check.timer` → next
09:00 ET.

### Rollback

`git checkout v0.3.19` for the repo. The unit files are **not** rolled back by
that — they live in `/etc/systemd/system` — so if you need to undo them, re-copy
from the v0.3.19 checkout and `daemon-reload`. In practice you would not: reverting
`argus-snapshot.service` restores the outage.

## Scope

Two threads, and only one of them was planned. The deploy mechanics are not part
of the config-profiles design — they are the migration's own fallout, the second
thing step 2 surfaced (v0.3.19 was the first). The backup work is the **third**,
and it is the one that had already gone wrong in production: v0.3.18's
`${ARGUS_ENV:?}` broke `argus-deploy.sh`, then the nightly snapshot, then every
documented compose command, and each was found only by going looking. **The class
is now closed by test rather than by memory** — no compose invocation anywhere in
this repo, executable or documented, can lose the profile without a test failing.

**Steps 3 and 4 are unchanged and still owed:** the cert flip of
`unmanaged_order_cancel`, then the live cutover. Both now arrive on a deploy that
runs the release's own steps, names what it is doing, and restarts only when a
restart means something.

**`docs/go-live-findings.md`'s NAS row moves to partly closed.** The pull is
hardened and now monitored end-to-end from a box that survives the NAS; what
remains is watching `argus-pull-check.timer` report `ok` for a few consecutive
days. Litestream's deferral makes that snapshot the only off-box copy, so the row
does not close until the check has a track record.

**Test suite: 2004 passing, up from 1999 at v0.3.19.**
