# v0.3.3

Two live-fire fixes from 2026-08-17 plus the control-surface gap reported during
the 2026-08-14 halt. Requires an image rebuild — this is a `src/` release. **No
config change**: `argus.toml` and `blackout_dates.txt` are unchanged from v0.3.1.

## Fixed

**Two spreads sharing a strike left both unwatched, and defeated the concurrency
rail.** The first session with two positions open at once broke on it. One
spread's short leg was the other's long leg (`20260817-put-7750-7745` and
`20260817-put-7755-7750`), `positions` is keyed by symbol and holds only the net,
and a row that nets flat is deleted — so the shared strike vanished and neither
spread could be reassembled. A live position sat with no virtual stop being
evaluated.

The same netting hit the gate. `open_spread_equivalent` was `ceil(broker_legs / 2)`
and the broker nets the shared strike too, so two spreads read as one, a third was
allowed, and ~2850 of max loss stood against a `daily_max_loss` of 2500. Chained
spreads generalize it: k of them present as 2 legs however large k is, so the limit
stops bounding anything at all. `signal.width = 5.0` against SPX's 5-point ladder
makes consecutive candidates chain by construction — this is the common case for
two same-side spreads, not an edge case.

Spread holdings are now attributed per TRADE IDEA, from
`order_legs.applied_quantity` — which already recorded it, so no migration. Two
ideas sharing a strike are never summed together. The gate takes the HIGHER of the
broker-derived and ledger-derived spread counts; the ledger can only ever tighten
the limit, never hand back a slot the broker says is taken.

An invariant keeps the attribution honest: the sum across all reassembled spreads
must equal `positions` symbol by symbol, and where it does not, the affected
spreads are reported rather than watched. That is also what stops an order ledger
retained across a sandbox reset from rebuilding yesterday's spreads as phantoms —
so the reset now clears `order_legs` alongside `positions`, keeping only the
`orders` identity rows that v0.3.2 actually needed.

**`/status` and `/kill` were unreachable during the 2026-08-14 halt.** Reported
by the operator during the incident. Two defects with one root cause — the
control surface's lifetime was tied to a successfully-started process.

The per-session reconcile mismatch halted the process, which shut down and took
the listener with it. Every restart after that failed at the *startup* reconcile,
which ran BEFORE the control server bound, so the surface never came back across
33 further restarts. For the whole event there was no `/status` to diagnose from
and no `/kill` to stop it — only SSH. This contradicted the stated non-negotiable
that `POST /kill` is always-on and phone-reachable.

The restart loop was also unbounded: `restart: unless-stopped` has no attempt cap
and systemd's `StartLimitBurst` guards the compose process, not the container
inside it. Each of 34 iterations re-announced the same unchanged condition, about
68 Slack messages, and would have continued all weekend.

**An unrecoverable halt now parks the process instead of exiting it** — halted,
unable to trade, and still serving. `_stop` means "stop trading"; the new `_exit`
means "leave the process" and only an operator signal sets it. The control server
binds before the reconciliation rail, so a rail that refuses no longer takes the
surface with it. `/status` reports `halted` explicitly, separately from the kill
switch, because they mean different things: engaged blocks new entries and
resumes tomorrow, halted means no further sessions until a human intervenes.

The alert storm needs no separate fix: a parked process never exits, so Docker
never restarts it. A process that dies from a genuine bug still exits non-zero
and is still restarted.

Nothing was trading on 2026-08-14 — the account was flat — so the loss was
observability rather than money. The case this actually guards is a mid-session
crash whose mismatch is caused by a real open position, where the position would
be both unmanaged and invisible.

**The unwatchable page repeated every 15 seconds, and fired on a window that
resolves itself.** Two separate faults on one path.

It had no edge tracking at all — Tier 1 plus an alert on EVERY watchdog refresh
while the condition persisted, which on 2026-08-17 was 66 Tier 1 records and a
page every 15s for one unchanging fact. An episode is now keyed on a signature of
what is unexplained: it pages once, stays Tier 2 while unchanged, and pages again
immediately if a genuinely different problem appears.

And the two legs of one multi-leg order book as separate fill events (~0.25s
apart), with `on_filled` refreshing the watchdog the moment the first lands — so
it aimed straight at the window where a spread legitimately has one applied leg.
That is post-fill propagation lag, which `watchdog.book_settle_s` already exists
to absorb, so it now governs both windows rather than adding a second knob meaning
the same thing. **No config change**: the key and its value are unchanged.

Both directions that mean a real position may be unwatched still page on the first
observation, with no allowance: `held_but_unbooked`, and a `positions` row no order
explains. Recovery is Tier 1 too — an operator told a position is unwatched is now
told when it is watched again.

## Operational note

A parked process shows as `active (running)` in `systemctl status`, the same as a
healthy one. It is distinguished by a single `process_halted` Slack alert, a
HALTED row at the top of `/status`, and a WARNING repeated to the journal every 15
minutes. **A halt still requires a human**: resolve the cause, then
`sudo systemctl restart argus.service`.
