*The kill switch promises to stop "an entry order already working at the exchange",
and it does that with one cancel request that swallows its own errors. P5 (2026-08-30)
built the backstop: register the order a walk left behind, and while the broker says
it is still working, ask again. On the real account that backstop has been in
observer mode since the cutover. It decides, records `would_cancel`, and sends
nothing. It stayed that way because its promotion waited on a cert track record, and
cert has not been able to place an entry since ~2026-09-02. Tastytrade now says the
sandbox fault has no ETA. This release switches the backstop on in live, on evidence
live can supply for itself.*

*Named per the Argus's Eyes convention. Rastaban, the pool's only name, is reserved
for dual-watchdog / consensus verification and does not fit, so the name comes from
outside the table. **Arcturus**, α Boötis, from the Greek *Arktouros*, **"guardian
of the bear"**: the star that follows the Great Bear around the pole and never lets
it out of sight. It qualifies by tradition, not by "eye" etymology, Alcor's standing:
a guardian is a watcher by definition. **The fit is the guardian that keeps
following.** This release is about an order Argus has already decided must not
stand, and about not stopping at the first request to end it: keep watching until the
broker says it is dead. The etymology is standard (the IAU name, attested in Hesiod),
and unlike Tarazed it needs no second-source check. **Rastaban stays reserved.***

## What changed

### 1. `watchdog.unmanaged_order_cancel = true` in `argus.live.toml`

The only behaviour change. P5's residual recheck now **sends** the repeat cancel on
the traded account, where since the cutover it only recorded
`order.residual_would_cancel`. Unchanged:

- **Opening orders only.** A closing order still gets a page and is never touched,
  under any grade or halt.
- **Only on a positive WORKING sighting.** Absent, unreadable and ambiguous answers
  neither resolve a residual nor authorize a cancel.
- **Direction comes from what Argus minted**, cross-checked against the identifier.
  A disagreement refuses.
- **Rate-bounded.** Backoff of 15 → 480s, then flat at `unmanaged_order_max_s = 900`.
- **Never rehydrated.** A previous process's orphan is still reconciliation's to find.

The outbound call is `stack.execution.cancel`, the same audited port every
walked-away entry already calls in live. Nothing new goes to the broker; there is
one new caller.

The comment block above the key is rewritten to say why the cert condition was
replaced and how to roll back.

### 2. The precondition moved from cert to live

→ [decision record](../decisions/2026-09-19-live-cancel-recheck-promotion.md). In
short:

- **The cert gate was not P5's.** P5's design said not to wait for a
  `would_cancel` record. The gate came in with config-profiles F2 (v0.3.17) and
  hardened into "until cert has a track record of the real re-cancel", which is an
  event, not a stage.
- **That event can no longer happen.** Cert has no entry path, so no opening
  residual can form there. Argus doesn't run in cert any more, and tastytrade gives
  no ETA.
- **Live needs it.** Without it, a `/kill` whose one cancel fails leaves an opening
  order resting on the real account. The worst a wrong re-cancel can do is leave a
  spread unopened.
- **The new gate** is live's own `order.residual_*` rows since the cutover. Every
  row must be Argus's own, opening, direction-consistent, and genuinely working when
  `would_cancel` fired. Zero rows also means promote. That is step 1 below.

## Why it's safe

- **It moves only toward less exposure.** The one new action is cancelling an
  opening order that the walk had already decided to cancel and that the broker says
  is still working. The worst case is a missed entry. A fill racing the cancel makes
  the DELETE fail harmlessly and books through `FillConsumer`. A partial fill leaves
  a smaller position than the gate approved, never a larger one.
- **The welded invariant is untouched.** `1 × 950 ≤ 950`, and P4 still counts a
  working opening order against the cap either way.
- **The decision logic has been running on live data since 2026-09-15** — with, as
  the gate read showed, nothing to decide about yet (§6). Only the call it guards is
  new, and that call is the existing `execution.cancel`, which `_request_cancel`
  sends on any walk that walks away whatever this flag says.
- **An AST test still pins exactly one outbound cancel in the module**, inside the
  one flag branch (`test_the_outbound_cancel_sits_behind_ONE_flag_in_ONE_place`).
- **No code path changed.** The image differs from v0.4.4 by one docstring.

### 1. THE GATE — read live's residual record (read-only)

Take the most recent nightly snapshot, which is already off the volume. It is in
`/path/to/backups/` on the droplet, and the NAS has a pulled copy. Never read
`argus-live.db` on the volume. Wherever the copy lives:

```bash
sqlite3 "file:argus-YYYYMMDD.db?mode=ro" "SELECT seq, ts, category, payload FROM audit_log WHERE category LIKE 'order.residual%' ORDER BY seq"
```

Replace `argus-YYYYMMDD.db` with the snapshot's actual filename. Then:

- **No rows:** pass. That is the expected result (§4 of the decision).
- **Rows:** each must pass all four checks in §4 of the decision:
  1. it is Argus's own identifier;
  2. every `order.residual_would_cancel` is on an OPENING order;
  3. no `direction_disagreement`;
  4. each would-cancel order was genuinely working at that moment. Check that one
     against tastytrade's order history for the account.
- **Any row fails: STOP.** Don't deploy. That's a defect in the decision logic, and
  it gets its own record.

The snapshot runs only up to last night. Anything from today's session is not in it.
Deploying after the close, before tonight's snapshot, leaves today's rows unread.
Check today's journal for `would re-request cancel of residual order` to cover the
gap:

```bash
sudo journalctl -u argus.service --since today | grep -c "would re-request cancel"
```

`0` closes the gap. Anything else: read those lines before going on.

## After deploy: what to check

1. **The sha, not the page.** `/status`'s `unmanaged` section names the mode only
   while a residual is outstanding. It shows `auto-cancel ON for opening orders`
   where it used to show `OBSERVER MODE (would_cancel)`. With none outstanding it
   reads `none working` on both versions, so on an ordinary day the config sha is
   the only confirmation.
2. **The first live re-cancel is an event to read, not a routine rail firing.**
   When it comes, it's a `residual_order_working` page followed in the audit log by
   `order.cancel_attempt` / `order.cancel_requested` from the recheck. Read the
   whole arc in the EOD review:
   - registration;
   - the working sighting past `exit_cancel_settle_s`;
   - the cancel;
   - the `resolved: dead` (or `filled`) that ends it.
3. **The case this does not prove.** An order stuck at `Cancel Requested` is still
   unexercised. The flag makes the system keep asking while it lasts; it does not
   show how tastytrade behaves in that state. The first
   `order.residual_cancel_failed`, or a residual past its second attempt, gets
   written up.

## 6. The gate read, and one correction to the decision record

Read on 2026-09-20 against the nightly snapshot `argus-20260919T163001.db`
(2026-09-19 16:30 ET, a Saturday — so it holds every live record through the
2026-09-18 session), read-only. Confirmed to be the live database: `seq` 1 is
`process.start {"environment": "live"}` at the 2026-09-15 cutover boot, running to
`seq` 59,877.

| Query | Result |
|---|---|
| `category LIKE 'order.residual%'` | **0 rows** — the gate passes on its zero-row branch |
| `category LIKE '%cancel%'` | **0 rows** — live has never sent a cancel DELETE, by any caller |
| `walk.finished` | **4**: two entries (09-17 `put-7585-7580` at 0.50, 09-18 `put-7595-7590` at 0.55) and two 15:31 ET flatten closes at −0.05. All `filled`, all `steps: 0`, all `cancel_requested: false` |
| `positions` | **0** (flat) |

Every live walk has filled on its opening limit, so nothing has ever walked away and
P5 has had nothing to register. **That is also why the cert gate was the wrong
instrument** — it waited on an event whose live counterpart has not happened either.

**The correction.** The decision record's §4 claimed production's acceptance of an
Argus cancel DELETE "is answered by every live walk that has ever walked away". No
live walk has walked away, so that claim is false and is withdrawn in §4.1. What
survives: the flag does not decide whether live ever sends a cancel (the walk's own
`_request_cancel` does, and it runs first); for the two dominant abandonment classes
P5's send is a repeat on an order whose cancel was already attempted through the same
port; and a DELETE production refuses yields `order.residual_cancel_failed` plus the
backoff, which is observer mode's outcome with a record attached. **The first live
re-cancel remains a first**, and stays on the watch list above.
