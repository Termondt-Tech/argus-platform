# v0.3.19 — Mizar

*One fix, found the hard way: **v0.3.18's own deploy failed**, and it failed on a
property of the deploy script that nothing had ever had to think about. The script
runs out of the working tree, so **the script that deploys v\<N+1\> is the one from
v\<N\>** — and v0.3.18 was the first release ever to change what the steps AFTER
the checkout must do. It now hands over: if the checkout replaced the script, the
run `exec`s the version the tag ships and that one finishes the job.*

*Named per the Argus's Eyes convention (`docs/releases/README.md`). Neither pool
candidate fits (**Aldebaran** stays reserved for the live-min-size flip or a clean
re-watch; **Rastaban** for dual-watchdog / consensus), so the name comes from
outside the table, the pattern since v0.3.6. **Mizar** — ζ Ursae Majoris — is
chosen for its pair rather than its etymology, and the pairing is the point:
**Alcor**, spent on v0.3.5, is the naked-eye companion that was the classical test
of eyesight, and Mizar is the star that turns out to be **two** when something
better looks at it (the first telescopic binary ever resolved, 1617). This release
is exactly that failure: the deploy could not see that a second, different version
of itself existed — it read one script where there were two, and ran the wrong one
past the checkout. It qualifies by **tradition, not "eye" etymology** — Alcor's
standing, already granted, and this deliberately claims the other half of that
pair. **Aldebaran and Rastaban stay reserved.***

**`scripts/argus-deploy.sh` + tests + docs. No `src/`, no config, no image.** The
plan will report `build: no` and `config: no`, which is correct and is itself worth
noting: **a script-only release is a third shape the plan does not name**, because
`scripts/` is in neither `BUILD_INPUTS` nor `CONFIG_INPUTS`. It needs a checkout and
nothing else — **no restart is required**, and skipping it avoids tearing down a
session for a change the running process cannot see.

## Fixed

**The deploy script hands over to the version the tag ships.** Immediately after
the checkout verification, it compares its own bytes against what it recorded
before the checkout; if they differ it `exec`s the new copy and lets that one run
the build, the unit sync, the restart and the read-backs.

The reasoning in one line: **everything after the checkout belongs to the release
being deployed, and the release is the authority on how its own steps are run.**
v0.3.18 is the worked example — it made `ARGUS_ENV` mandatory for every
`docker compose` invocation, and v0.3.17's script, having already checked out
v0.3.18's compose file, ran an unprefixed `docker compose build` and died on
`${ARGUS_ENV:?}`. That left the droplet half-deployed: new tree, old systemd unit,
nothing built, and a `systemctl restart` away from a crash loop.

**Two details that are easy to get wrong, and one of them is silent:**

- **`ARGUS_DEPLOY_PREV_TAG` is carried across the hand-over**, and without it the
  fix would be worse than the bug. The handed-over run re-derives `PREV_TAG` from a
  tree that is *already on `$VERSION`*, so `git diff $VERSION $VERSION` is empty,
  `NEED_BUILD` comes back 0, and it **skips a build the first run had correctly
  planned** — a green deploy that silently reattaches to the previous image, which
  is precisely the failure the version read-back exists to catch, re-introduced one
  layer up.
- **It cannot loop.** The handed-over copy computes its "before" hash from the file
  it already is, and its own checkout is a no-op, so the hashes cannot differ twice.
  `ARGUS_DEPLOY_REEXECED` is belt-and-braces against a checkout filter that rewrites
  on every pass, and it refuses rather than recursing.

**It also closes a quieter hazard that was there all along: bash reads a script
incrementally.** A checkout that rewrites the file mid-run can make the *remaining*
lines come from a different version, at an arbitrary byte offset. That has been
true of every deploy this repo has ever done and has simply never bitten. The
`exec` makes the boundary explicit instead of leaving it to file offsets.

## Added

Two assertions in `tests/test_deploy_wiring.py`, both pinning the incident rather
than the code:

- **the hand-over exists, and carries `PREV_TAG`** — with the "before" hash taken
  before the checkout and the "after" hash taken after it, which is the whole
  mechanism;
- **every `docker compose` invocation in the script carries `ARGUS_ENV="$PROFILE"`**
  — the v0.3.18 failure, pinned exactly. Compose refuses when it is unset, on
  `build` and `run` and not only `up`, and **sudo scrubs the environment**, so it
  must be on sudo's own command line rather than exported. `docker tag` /
  `docker images` are excluded deliberately: plain docker never parses the compose
  file.

Verified end to end against a scratch repository — two tags, a source change and a
script change — confirming that the hand-over fires exactly once, that the
handed-over run still plans `build: YES` from the original `PREV_TAG`, and that
`ARGUS_ENV` reaches the compose build.

## Deploy

**No restart, and therefore no session teardown.** The change is to the deploy
script itself; the running process cannot see it.

```bash
cd /opt/argus
git fetch --tags
git checkout v0.3.19
git describe --tags && git status --short     # must be the tag, must be clean
```

Running `scripts/argus-deploy.sh v0.3.19` also works and is harmless — it will
plan `build: no`, hand over to v0.3.19's own script (the first live exercise of
the new path), and restart the service for a change it does not need. Prefer the
plain checkout unless you want to watch the hand-over happen.

**Rollback is `git checkout v0.3.18`.** Nothing else moves.

## Scope

Not part of the config-profiles design — it is the migration's own deploy
